# Plan, 2026-11-25: what the working binders do that Sprava does not

Status: working plan, revised once after a critique against the code (2026-11-25). It follows `docs/plan-2026-11.md`, whose tracks merged, and replaces nothing in the design
docs. It says what Sprava takes from the lifeproj binders the author works in every day, in what order, and who
does it. The decisions are D45 to D49 in `docs/decisions.md`. Examples are invented.

## 1. Objective

A binder in Sprava gets better at its own work the way a lifeproj binder does, with more structure than
lifeproj has:

1. **It learns rules.** Its Claude proposes a rule; the person accepts it on a card.
2. **It automates itself.** Its Claude writes scripts in the binder and runs them during a turn.
3. **It suggests an add-on.** A script or a workaround that keeps recurring becomes a suggestion in a built-in
   Improvements binder.
4. **A release ships the add-on.** Development turns suggestions into built-in importers and exporters
   (decisions.md P17), and the binder's script is retired.

Around that loop: the outgoing mail loop is closed (what was placed, what was sent), and Sprava says how well
each page of a document was read.

## 2. Where this comes from

On 2026-11-25 the lead asked the agents of three working lifeproj binders how they work: the hub, a binder
with a heavy mail and drafting routine, and a records binder with several years of scans. The lead read none
of their files (`AGENTS.md`, "The repository is public"); each agent answered in its own words. No binder
content is repeated here.

What they would not give up, and what Sprava has for it:

| They keep | Sprava today |
|---|---|
| One catalog with a validator and views built from it | Has it: typed ops, the guard, the op log, Undo |
| Original files kept byte for byte; tools that stop when unsure | Has it |
| The person's approval before anything leaves, checked again after | Half: a draft is approved and placed in Drafts; nothing checks what was placed or what was sent |
| A manual the agent rewrites as it learns | Missing: only the person writes Instructions (D43) |
| Scripts and skills the agent adds and tests in the binder | Half: scripts run in a turn (D36); no secrets for them, no schedule, no path to a built-in feature |
| A gate on scans that could not be read | Missing: OCR confidence is thrown away, and a search does not say what it could not read |
| One list on the phone | Built, not deployed (`docs/plan-2026-11.md` §5) |

What cost them most: facts repeated without checking the source, a mail export that changed what it carried,
to-dos that were stale the morning after a meeting, tools that failed without saying so, and one scanned page
nobody could read that held a rule that mattered.

Where Sprava is already better: every change is a typed op with Undo, one supervised runtime with a Health
line instead of several loops and daemons, a sandbox around the agent, per-host web prompts, a tested backup
with a restore drill, and a phone path that is end-to-end encrypted.

## 3. Tracks

Each track is a series of small PRs through the gate (`AGENTS.md`), each in its own worktree. The work is
divided between two sessions on two Macs, which coordinate by orchestra mail (section 4). A session messages
"ready to merge #N" and waits for the author's go.

### Track P: a dry run of adding a lifeproj binder (`preflight`)

The author will add one lifeproj binder by hand; none is moved by Sprava's own doing yet. Before that, the
same steps run on an invented folder shaped like one: 301 invented documents with a catalog, a manual, a
hand-written dashboard, a `scripts/` folder, files in `intake/` and a folder of raw archives.

What the app does today (read from the code, and run through `sprava dev` where it can be): Add Folder puts
the folder on the Shelf and writes nothing in it; the binder page then offers Adopt, and until adoption the
page is read-only (no drop, no to-dos, no cards, no Claude). There is no import as a copy (P20): adoption in
place is the only path.

Found so far, worst first:

1. Adoption refused any binder with more than 100 catalog rows (#688). Fixed in its own PR: the mechanical
   fixes are one write, and the invented binder adopts in a second.
2. A folder whose name differs from `meta.name` reads "needs attention", and the Adopt button is not shown.
3. A document record with a bad date or no title blocks the stamp, and no card repairs it.
4. Every to-do with no date gets a card of its own: 20 cards for 40 to-dos here.
5. The old manuals are never set aside at adoption, so the Instructions tab's "copy in the old manual" button
   never appears; an `AGENTS.md` over 16,000 characters cannot be accepted.
6. A script runs only through an installed interpreter (`python3 scripts/x.py`), never directly or from a
   virtual environment in the binder. Skills and hooks in the folder are ignored.
7. Bounds to know: a drop takes 200 files and one folder level; Claude reads 100 intake documents a day; a
   folder under iCloud Drive or `~/Library/CloudStorage` is refused; repeating to-dos stay off while lifeproj
   can reach the binder.

Done when: each finding is fixed or filed, and the invented binder goes from Add Folder to a first
conversation in a development build with no step by hand outside the app.

### Track D: document tools (`conversation-documents`), D45

Goal: Claude keeps the document record for what a drop does not cover.

Drag and drop stays the way documents arrive. Claude gets tools for the rest: catalogue a file it wrote in the
binder (a brief, a summary), rename or refile a document, correct a record's fields, add a log entry. They
follow the to-do tools (D32): each call is an op through the guard, applied in the turn, checked against the
record as the turn found it, counted against a limit per turn, and undone with the turn. `ConversationClass`
(D3) classes these ops but nothing calls it; D45 amends D3 and `docs/conversation.md` §6.1 for them.

Undo is most of the work. Today only `move_document` has one (`Undo.swift`). Three PRs:

1. Rename, refile and correct: tools over `move_document` and `update_document`, with an undo for
   `update_document`.
2. Cataloguing a file Claude wrote: `file_document`, a new `unfile_document` op as its undo, and the turn's file
   Undo taught that the catalog's documents may change in a turn (`TurnHistory`, `docs/conversation.md` §18.4).
3. The log entry: a tool over `add_log_entry`. The entry stays when the turn is undone, and the turn's line says
   so. The author, 2026-11-26: "Log entry stays, logs are for traceability." The format agrees: a log entry
   records a fact and is never undone (binder-v0 §6.10).

Tier B (`Undo`, `TurnHistory*`, `OpApplier`). Tested refusals: a path outside the binder, a key file, a record
changed since the turn read it.

Done when: "file the summary you wrote" changes the catalog in one turn, and Undo puts it back.

### Track L: learning (`binder-learning`), D46

Goal: a binder's Instructions grow from the work, and the person approves every line.

1. A card kind for a proposed rule, on the draft card's pattern (a saved proposal Sprava trusts and records,
   with its own approve path), and the command that accepts one. Accept appends the rule, dated, under a
   `## Learned rules` heading in the person's part of `AGENTS.md` by the `save_instructions` path: the digest
   check, the atomic write, Undo last save. Accept is refused while the text on disk is not the accepted one
   (changed outside the app and never confirmed): a save would accept that text too. The card then says to
   confirm Instructions first. It is also refused, with words, when the person's part is full.
2. A conversation tool, `propose_rule`, in a file of its own: one line of at most 500 characters, a reason, and
   what it is about (filing, drafting, routine). Checked when proposed: no marker line, no control characters,
   nothing code itself reads from `AGENTS.md` (the lifeproj addendum's commands). It never applies in the turn.
3. The session's instructions change: `AGENTS.md` is written by the person, or accepted by them a line at a
   time. They say when to propose: the person says to remember something, or corrects the same thing a second
   time. A document asking for a rule grants nothing.
4. The card in the app: Accept, Edit, Dismiss, with the rule and its reason shown whole.
5. Corrections (D11): after the person undoes a filing and files it differently, the next message's line from
   Sprava says so. Paths go in as quoted data, since a file's name comes from a document.
6. Consolidation: a proposal may replace the whole `## Learned rules` section; the card shows both.
7. Drafting voice, after Track M files sent mail: before drafting, Claude reads a few of the person's own sent
   messages in this binder.

Known limits, stated in the design: Undo last save is one level, so a second Accept ends the first one's Undo
and an older rule is removed on the tab; an accepted rule guides the conversation, which has a shell and the
web, as well as filing, so the card is the control; the on-device reader stops at its token budget.
`docs/conversation.md` §6.2 and §8.1 and `docs/binder-instructions.md` §4.4 are amended with it.

Tier B: model output becomes text the reader of intake follows.

Done when, on an invented binder: "remember that notices from the building manager go in `notices/`" makes a
card; Accept puts the dated line in Instructions; the next dropped notice is filed there; Undo last save
removes the line.

### Track I: the Improvements binder (`improvements`), D47

Goal: what a binder cannot do, or keeps doing by hand, reaches development without anyone reading the binder.

1. General is hard-coded in `Shelf` and `Services`. First PR: built-in binders as a short list, with General
   the first and Improvements the second, made on first use, kept on this Mac's Shelf (D26).
2. A card kind for a suggestion, and a conversation tool, `suggest_improvement`: a title, what was attempted,
   what stood in the way or what keeps being repeated, and a script's path when there is one. The script's
   bytes are read when the card is made, under the draft card's rules (inside the binder, never a key file,
   a size bound). The card shows the whole text. The person may edit it. Approve puts it in the Improvements
   binder as a private to-do with its note.
3. A warning on the card when the script holds what looks like a key: until secrets for scripts are built, a
   script may carry one inline.
4. Counts by code, never content: per binder, script runs, refused commands and hosts, files held and why. A
   script run many times makes a suggestion card of its own.
5. Export: the runtime writes the approved suggestions to one Markdown file in a folder the person picks in a
   save panel. The person files them as issues. Development sessions do not read the Improvements binder.
6. A suggestion built into a release is closed with the release's note.

A suggestion crosses from one binder to another; D16 and `docs/conversation.md` §17.4 say a session never gets
cross-binder access, and this keeps to it: the session writes a card in its own binder, and the person's
Approve carries it over.

Until an add-on ships, the binder's own script does the job in a turn. Secrets for scripts are designed
(`docs/conversation.md` §18.3.2) and wait for the author's go; scheduled runs come after that.

The first candidate is known: an importer for a hosted task board, which one binder now pulls by script.

Tier B: model output becomes a card, and Export writes outside the binder.

Done when: on an invented binder, a suggestion with a script is approved after an edit, appears in
Improvements, and the exported file holds exactly the approved text.

### Track M: the mail loop (`mail-loop`), D48

Goal: Sprava knows what was placed in Drafts, what was sent, and whether it was what the person approved.

Built into the IMAP draft exporter (`docs/integrations.md` §5.2). Today the approved message's bytes are
removed once placed and nothing of it is kept, the draft card names no to-do, and a connection has no Sent
folder. So:

0. A check before the design is fixed: which mail programs keep a draft's Message-ID when they send it. One
   invented message through the author's mail program and bridge.
1. A record of each placed draft, kept 30 days in Sprava's state: its Message-ID, recipients, subject, and the
   hashes of the body and of each attachment. Never the text.
2. Read-back: after placing, fetch the draft by Message-ID and compare it with the record. The card says
   "placed as approved" or what differs.
3. The Sent folder: found by the server's own mark for it, else chosen in the connection's settings.
4. Sent matching: the job searches the Sent folder for the Message-IDs in the record, and reads nothing else
   there. A match by subject and time would mean reading other sent mail; it waits for step 0's answer.
5. On a match: a card that says whether the sent copy is the approved one or what changed, and on Approve
   files the sent copy, adds a log entry and sets the to-do the draft named to waiting with a follow-up date.
   The draft tool gains an optional to-do id for this. A card, since `docs/conversation.md` §6.1 applies nothing
   Sprava started without a tap.
6. Staleness: a draft card that has waited shows its age and how many messages arrived in its thread since it
   was written.
7. #592: a draft that failed to reach the server shows on the binder page with Try again and Discard.

D48 amends D41, which allowed no IMAP command beyond what placing a draft needs.

Tier B (`Sources/Capture/IMAP/**`, `DraftPlacing.swift`).

Done when, against the test IMAP server: a placed draft is read back; a sent copy with one recipient added is
matched and its card says what changed; Approve files it and sets the to-do waiting.

### Track E: reading coverage (`reading-coverage`), D49

Goal: the person and Claude know which pages Sprava could not read, and a search never passes off "could not
read" as "is not there". This builds the page and legibility part of D17.

Part of it exists: the index counts pages read by OCR and pages it could not read (`Retrieval/Coverage.swift`),
and `search_binder` returns how many sources were not fully read. What is missing is the grade of a page that
was read badly, any display of it, and a way for the person to supply what a page says.

1. The helper returns one block of text today. First: it returns text by page, with how each page was read and
   the recognizer's confidence, which the OCR step discards now (`ExtractHelper.swift`, tier B; an interface
   between `Extract` and `Retrieval`).
2. Grades in the index: good, poor or unreadable for each page; a page whose text layer holds almost nothing
   for its size is graded too. A document with many pages stops counting as a gap for that alone.
3. Show: the filing card says "page 3 of 5 was hard to read" and opens the page. Explore marks the document.
   The binder lists documents not fully read.
4. The person's reading: on that list the person types what a page says. It is a record in the binder (the index
   is rebuilt from the binder), searchable and marked as theirs. A page marked as read with no text typed stays
   counted as not searchable.
5. Search: every `search_binder` result names the documents with pages that could not be read, and code repeats
   it in the turn's summary line. The session's instructions say to look at a poor page as an image before
   relying on it.
6. Files with no record: only `intake/` is carded today, and a file elsewhere with no record is neither listed
   nor searched. A folder marked "keep as is" in the binder's settings is indexed by file name and text, and
   never carded.

Tier B for steps 1 and 4; otherwise tier C.

Done when: an invented five-page scan with a rule on a blurred page 3 is filed and flagged, and a search for
the rule answers that it was not found in readable text and that one document has a page that could not be
read.

## 4. Order and shared files

1. P first: it is short, and the author's own add depends on it.
2. D and L, one session, D first. Both add to the conversation's tools and its instructions.
3. I beside them, its own worker; it rebases onto L and D for the tool table.
4. M: steps 1 to 3, 6 and 7 do not depend on step 0 and start at once; steps 4 and 5 once it has an answer.
5. E: decided on 2026-11-26; it starts when M's first PRs are in review.

`Sources/Services/Claude/ClaudeConversationPolicy.swift` gets a sentence from L, D, I and E; whoever merges
second rebases. Merges that change Swift go one at a time, in the order the lead sets.

Two sessions share the work, by the author's instruction of 2026-11-25:

| Session | Builds | Checks |
|---|---|---|
| The lead, on the second Mac | P, D, L, I | M and E: runs each "Done when" on a development build from the other session's branch |
| The session on the author's main laptop | M, E, and the backup fix for a lock left by a killed run | P's fixes, D, L and I, the same way |

The split follows the files: D, L and I share the conversation's tools; M is the IMAP code, and its step 0
needs the mail program on the main laptop; E is the extractor and the index. The session that builds a track
writes its tests and takes it through review. The other session runs its "Done when" on its own Mac, on
invented binders only, before "ready to merge" is sent, and reports what it saw. A finding goes back as orchestra
mail on the track's task, never as a change pushed to the other session's branch.

## 7. Risks

- **A flood of cards** when many files are dropped at once. Track P measures it.
- **A leak through a suggestion.** A script can hold a board id or a name. The card shows the whole text, and
  nothing leaves the Mac before Export.
- **Instructions that only grow.** L's step 5.
- **A rule planted by a document.** Claude may propose what a document told it to. The card shows the rule's
  text and reason, and nothing is saved without the tap.
- **A wrong sent match.** A fallback match is a card, never applied by itself.
