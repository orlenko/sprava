Example"), `kitchen-reno`, `tax-2026` and `rental-elm-street`, people such as "A. Example", "the notary" and "the property manager". Nothing here comes from a real binder.

This draft puts operability first. Every component is treated as something that will stop at three in the morning and must be noticed and restarted without a person. Silence is an alarm. ## 1. Overview and principles

### 1.1 What Sprava is

Sprava keeps one binder per episode of a person's life: an estate to settle, a renovation, a tax year, a rental property. A binder is an ordinary folder on the Mac. The format of that folder is called a teka. Inside it, a file called the catalog (`catalog.json`) says what is open, what is due, who the person is waiting on, and which documents exist. Sprava keeps that current truth up to date and keeps a record of how it got there.

The software has five parts.

- The app. A window with a shelf of binders, a Now page for each binder, a review queue of proposed changes, a Today page across binders, and a Health page that shows whether the background work is running.
- The runtime. One background program that macOS starts at login and restarts if it stops. It watches for new material, checks deadlines, keeps backups and search indexes, serves outside AI tools, and runs the clerk. Every change it makes to a binder passes through the transaction guard, the code that checks a change against the format's rules before writing it.
- The clerk. Apple's on-device language model (decisions.md P3). It reads one capture at a time, splits it into items, pulls out dates, amounts and names, and guesses which binder each item belongs to. It never changes anything. It proposes, and the person decides.
- The brain. Optional (decisions.md P1). Any AI tool that speaks MCP (the Model Context Protocol, an open standard for connecting AI tools to data) can read the binders the person allows and propose changes. Nothing a brain says is applied until the person approves it in the app.
- The capture folder. A folder the person chooses. holos, the author's dictation app, writes one small file there for each finished dictation or meeting (decisions.md P7). The app writes the person's typed notes and dropped documents there too. Sprava reads those files and nothing else of holos's, and never links holos code (decisions.md P6).

The work is split into three tiers (decisions.md P1). Tier 0 is plain code with no model: deadlines, the Nudge bucket for items waiting on someone else, recurrence, the cross-binder roll-up, backups, health. It must be useful on its own. Tier 1 is the clerk. Tier 2 is a brain. A change to a binder is an op: a small typed operation such as "add item" or "complete item". A proposal is a batch of ops waiting for the person's approval. Tier 1 and Tier 2 only ever produce proposals.

### 1.2 Principles

1. The folder stays yours. A binder is readable with any text editor and stays valid for lifeproj and terminal agents. Sprava adds one hidden folder, `.sprava/`, writes `catalog.json` only through ops, regenerates `DASHBOARD.md`, and leaves everything else alone (decisions.md F1). A few small exceptions come from the format drafts and need the author's acceptance: the lock file `.teka.lock`, filing a document into a document folder, `intake/_converted/`, and the visible `captures/` folder for filed captures (teka-v0 §9.7; capture-event-v0 §9; section 13 item 36).
2. One process to watch. There is one runtime. It writes a heartbeat. The app shows its age, and a tiny second job catches some failures while the app is closed (3.3). If the heartbeat is old, that is the alarm (decisions.md A1, M3).
3. Every job is boring. A job has a name, a trigger, a time budget and a rule that makes running it twice safe. A job that overruns is cut off and counted. Repeated failures pause it and the Health page names it.
4. One gate, and the person approves. Every write is an op checked by the guard and recorded in a log. Nothing proposed is applied without the person's approval, and everything applied can be undone (decisions.md A2, A5).
5. The clerk files, the brain thinks. The on-device model works on one capture plus a few retrieved facts within a 4,096-token budget. Anything bigger is a job for a brain (decisions.md P2, P5).
6. Nothing leaves the Mac unless the person sets it up. Section 10 is the whole list, and the app shows the same list with live counters (decisions.md A7).
7. Every piece has a name. Section 2.4 lists each moving part, why it exists and what breaks without it. The Health page shows each one's last success.

### 1.3 Trust boundaries

A trust boundary is a line between two parts where one side must not assume the other is honest or correct. Sprava has six. Later sections say which boundary they defend.

1. The Mac and the world. Nothing crosses this line unless the person turns a channel on. Section 10 lists every channel.
2. One binder and the others. A binder's contents stay inside its folder. Cross-binder views (the Today page, the roll-up, search across binders, MCP answers) see a binder only through its `disclosure` setting (full, title, kind or none; decisions.md F6). A binder set to `none` does not exist for those views (sections 7.6 and 11).
3. The runtime and other programs on the Mac. The runtime trusts the app, identified by its bundle identifier and its team (2.1). Approval and every change that widens what leaves a binder are reachable only from the app's own window, never through a URL scheme, AppleScript, Shortcuts or other automation, and the widest of them also ask for Touch ID or the password (2.1). The runtime trusts nothing else: shims, brains, terminal agents, the holos producer and every other program are sources of data, never of commands (sections 3, 7.2 and 8). There is one deliberate exception. Completions that the hub leaves in the spool's outbox close items without a card, because they are the person's own check-offs and lifeproj applies them the same way (decisions.md A8, F8). Section 11 names that channel and limits it.
4. The clerk and the text it reads. The clerk's instructions are fixed text shipped with the app. Captures and retrieved facts reach the model only as the prompt, as labelled data. The clerk can emit an interpretation, never an op (section 5; decisions.md C3).
5. A brain and the binders, over MCP. A brain has its own identity per client. On the MCP surface it reads what its scope and each binder's disclosure allow, and it may only propose. It never applies, never approves, and never learns over MCP that a binder outside its scope exists (section 7). This boundary covers the MCP surface only. Most brains (Claude Code, Codex, Cursor, VS Code, Gemini CLI) also have their own file and shell tools and run as the person. With those tools they can read every binder folder directly, and scope and disclosure do not apply. The MCP local-server guide calls configuration allowlists "cooperative boundaries" (web-mcp-agents). A binder that no agent may see needs the client's own controls, which Sprava cannot verify (7.5).
6. The backup and the place it is stored. Everything that leaves for offsite storage is ciphertext whose key stays with the person (section 9; decisions.md A6).

| Another program running as the same user | Read binders; talk to the runtime's socket; launch the shim with someone else's client id; forge capture events, proposal files, op-log lines or outbox completions | macOS puts no wall between one user's programs, and the design does not pretend otherwise. There is no network listener | Malware running as the user can read the user's files and the client's config. Registering the holos folder as a producer is bookkeeping, not authentication (section 8) |

Cloud folder names may reveal binder names: a cmirror project set up by lifeproj stores its mirror in a folder named after the binder (9.1) |

| Sprava's own bugs, and other writers' accidents | Nothing; the risk is damage | The hash-chained op log, the binder lock with a compare before rename, atomic writes, undo by compensating ops, external-edit detection, the doctor command (sections 4 and 12) | A bug that writes a valid but wrong catalog is caught only by the person reading the queue and the history. A program that skips the lock can still lose an update in a short window (4.5) |

### 1.5 Words used in this document

Each term is also defined where it first matters.

- Capture event: one immutable record of something the person said, typed or dropped in (decisions.md C1).
- Derived event: a reading of a capture made later, such as the clerk's interpretation (decisions.md C3).
- Interpretation: the clerk's typed reading of one capture: the items it heard, with time words, amounts, people, a binder guess and the quoted source words.
- Shim: the tiny program a brain launches to talk to the runtime (section 7.2).
- Spool: the shared folder the author's existing cross-binder tool (the hub) reads. A slice is the summary of open items a binder publishes there; the outbox is where the hub leaves the person's check-offs for a binder to apply (section 11).
- launchd: the macOS service manager. A LaunchAgent is a background program it starts for the logged-in user.
- Idempotent: doing something twice has the same effect as doing it once.
- Circuit breaker: a switch that pauses a job after repeated failures and retries it later, so one broken part does not fail over and over.

## 2. Components

### 2.1 The parts

- The app. A Mac app shipped first as a notarized DMG, a disk image that Apple has scanned and approved (decisions.md P4). Screens: the Shelf (all binders, each with freshness and a count of pending proposals), each binder's Now page, the review queue, the Today page, settings, and the Health page. The app reads binders from disk to display them and never writes one. When the person approves a proposal, edits an item or adopts a binder, the app sends the command to the runtime over XPC (Apple's local messaging between an app and its own helper). A Team ID check alone would admit every program signed by the same developer, the shim and holos included. So the runtime accepts a connection only when the peer meets a code-signing requirement that pins the app's bundle identifier as well as the Team ID, and both are built with the hardened runtime and no library-validation exception. The research did not cover XPC peer validation, so this is a spike (section 13). Every XPC session starts with a protocol version. Every request has a timeout on the app's side (proposed: 5 seconds for reads and status, 15 seconds for Approve, Edit and Undo), because an XPC reply handler otherwise waits until the connection breaks, and a runtime stuck on one binder keeps beating. On a timeout the app says "Runtime not answering (pid N); the request was not applied" with a Restart button, and leaves the card where it was. On the runtime side each request runs as a job with that budget (3.4), so the watchdog can mark a stuck request wedged and name it. The app reads the heartbeat file for health, so it can tell that the runtime is dead even when nothing answers.

  Build check. When the heartbeat's `build` is older than the app's own and the app runs from the registered bundle path, for example after an update replaced the bundle while the old runtime kept running, the app restarts the runtime. It never restarts a newer runtime from an older app. When the app's build is older, or it runs from a path other than the registered one, it says "Another copy of Sprava is installed at <path>; use that one or remove it" and changes nothing (3.1). The runtime also notices on its own when its executable is replaced (its inode changes) and restarts itself at the next quiet moment, so an update the person never follows by opening the app still takes effect (7.2).

  Commands only from the window. Approve, Edit, every change that widens what a binder shows, scope changes, client registration, the spool root and the backup settings are reachable only through the app's own controls. None of them is exposed through a URL scheme, an AppleScript dictionary, App Intents or Shortcuts, Services, or drag and drop. A Mac app can be driven by all of these, and by accessibility or computer-use agents that a brain may run. Widening changes and client registration also ask for Touch ID or the login password (LocalAuthentication), which UI automation cannot supply. The research did not cover these entry points, so this is a spike (section 13, item 39). If the runtime is not running, the app still shows everything, puts a read-only banner at the top ("Runtime stopped 7 minutes ago") with a Start button, and disables Approve, Edit and Undo. A second writer would bring back the race the single runtime removes. While the runtime is down, the app computes the buckets itself from the catalogs and today's date, with the same Tier 0 code the runtime uses, so a stale cache never shows yesterday's Today as current (3.4). If one binder's catalog crashed the app's own parser at its last launch, the app skips that binder and shows it as "cannot display", so one bad file cannot lock the person out of the Health page. Review cards come from the runtime over XPC, checked against the digest the runtime recorded for each proposal (4.6); while the runtime is down the app may show proposal files read-only, marked "not verified".
- The app's own captures. A typed note or a dropped document does not take a special path. The app writes a capture-event file into its own device folder under the capture root, exactly as holos does, and the runtime picks it up (capture-event-v0 §8.1, §8.2). One pipeline, one journal, one set of test fixtures. Each time it writes one, the app also tells the runtime over XPC the event id and its SHA-256, so an event that appears in that folder without such a notice can be told apart (section 8).
- The runtime. One user LaunchAgent registered from the app bundle (decisions.md A1). One process. It holds the supervisor (lease, heartbeat, watchdog, breakers), the jobs, the transaction guard, the clerk, and the MCP listener.
- The clerk. Swift code inside the runtime process using Apple's `FoundationModels` framework (decisions.md P3, A3). The fallback open model plugs into the same session code through the `LanguageModel` protocol; shipping one is deferred (decisions.md P3, M2).
- The extraction helper. Text extraction from documents and media probing run in a separate small helper, started by the runtime for one file at a time. It is sandboxed, has no network and no Keychain access group, reads a file descriptor the runtime passes to it, and returns plain text with a size cap. Documents come from other people and from brains, and a parser bug in the runtime itself would expose the key that makes seals mean anything (4.1). A crash kills only the helper.
- The MCP listener and the shim. The listener runs inside the runtime on a Unix domain socket, a local connection that exists as a file and never touches the network. Each connected brain starts its own shim, a small signed program in the bundle that speaks stdio (standard input and output, which is how MCP clients launch local servers) and forwards messages to the socket (decisions.md A4).
- The slice projection. One module is the only code path by which the Today page, the roll-up, the hub slice and the MCP listener read a catalog. It applies the binder's disclosure and each item's `redact` and `slice_title`. Inside one process there is no federation boundary to rely on, so this code path is the federation (sections 7.6 and 11).
- The index. One rebuildable full-text index per binder at `.sprava/index.sqlite`, built on SQLite (the database engine built into macOS) and its FTS5 search module (decisions.md A3). It serves the clerk's few retrieved facts and the app's search.
- Backup. A ciphertext-only mirror of each binder folder to a cloud-synced folder, through cmirror (the author's existing encrypted-mirror tool, built on the age file-encryption format) where it is installed; native later (decisions.md A6).

There is no other database, no web server and no network listener of any kind.

Retention of Sprava's own logs (proposed). Append-only files must not grow without limit, because a disk filled by Sprava's own logs would break the heartbeat write, the very alarm this design relies on. `jobs.log`, `lease-refusals.log` and each `mcp/audit/<client>.ndjson` rotate at 10 MB and keep 5 files, and none of them is backed up. `today/ops.ndjson` rotates the same way and is backed up. `capture/journal.ndjson` is compacted into a per-event state index: an event filed more than 90 days ago is kept only as its id and the op ids that filed it, which is all deduplication and restore checks need. The Health page shows the disk space Sprava's own state uses, and the doctor flags growth.

Where binders and the capture root may live. A non-technical person will often adopt a folder in Documents or in a Dropbox folder. A synced folder breaks several assumptions. Files there may not be downloaded yet, so a read can block for minutes. The sync engine is itself an outside writer and makes conflict copies such as `catalog 2.json`. Two Macs signed in to the same account would run two runtimes on one binder, and the lease is per Mac. In v0 the app therefore refuses to adopt a binder, or to use a capture root, inside a known sync location (`~/Library/Mobile Documents`, `~/Library/CloudStorage`, and Desktop or Documents when iCloud syncs them), and says why. An opt-in synced capture root for a phone follows capture-event-v0 §5.1, encrypted file by file. Each binder also carries a device owner record in `.sprava/owner.json` (a device id and the runtime instance), and the guard refuses to apply ops to a binder that another device owns. The device id is generated once per Mac and kept in the Keychain as a this-device-only item, never in a file that Migration Assistant or a restore would copy, so two Macs can never both claim to be the owner. A binder whose owner record names another device (after Migration Assistant, a restore onto a replacement Mac, or `lifeproj restore`) is read-only, with a Health line and a card: "This binder was last managed on another Mac. Manage it here?" The card is offered only when the last op from that device is older than 24 hours (proposed); otherwise it says the other Mac may still be using the binder. On yes, the guard appends a `takeover` op naming both device ids and rewrites `owner.json`. The restore drill includes this step (9.3).

Binder reads and writes run per binder with a timeout, off the guard's queue for other binders, so one slow folder never stalls the rest. The binder lock is never waited on: the guard takes it with `LOCK_NB` and retries for at most 10 seconds (proposed). After that the binder enters the state "busy: another program holds the binder lock", its writes are skipped and retried later, and every other binder carries on. The Health page and the card name the holder when they can (the process that has `.teka.lock` open), for example "lifeproj, pid 812". A `lifeproj` command suspended in a terminal would otherwise hang approvals, and a blocking `flock` cannot be cancelled (3.4). A background agent that reads Documents or Desktop may trigger macOS privacy prompts that nobody can answer at 3 a.m. Which permission the person grants, and what the runtime sees when it is denied, is a spike (section 13). The Health page then says "Sprava cannot read ~/Documents/kitchen-reno: permission". Detection of sync locations, Time Machine and Spotlight is not in the research and is part of that spike (section 10).

### 2.4 The complexity ledger

This design has more moving parts than a folder and a file. Each one is listed with the reason it exists and what goes wrong without it.

## 3. The supervised runtime

This section defends boundary 3 and the principle that silence is an alarm. It replaces the process zoo of the terminal workflow: separate sessions, a watcher daemon, a sync loop in a side pane and a web server (HANDOFF "The process zoo is fragile").

### 3.1 Registration from the bundle

The runtime is registered with `SMAppService.agent(plistName:)`, Apple's API for registering agents from inside an app bundle (macOS 13 or later). The property list lives inside the signed bundle at `Contents/Library/LaunchAgents`, and its `BundleProgram` points at the helper at `Contents/MacOS/sprava-runtime` (web-localfirst-platform: Apple's SMAppService documentation and Apple's developer support in forum thread 745009). Because the plist and the helper are inside the signed bundle, nobody can change them without breaking the signature, and a temp-file cleaner cannot delete them (same source).

Why a user agent and not a root daemon: whether Foundation Models works from a root daemon outside a login session is unknown, while all evidence shows it working from processes in the user's session (decisions.md A1; web-apple-fm). A root daemon would also need an administrator's approval (web-localfirst-platform: SMAppService `register()` documentation). The agent is not sandboxed in v0 because the app ships as a notarized DMG with the hardened runtime (decisions.md P4). If the App Store route is taken later, a sandboxed app may register only sandboxed helpers (web-localfirst-platform: enforced since macOS 14.2).

The plist (proposed):

- `KeepAlive` true. launchd keeps the job running and restarts it after any exit, clean or not (web-localfirst-platform: `man launchd.plist` on macOS 27.0). Turning Sprava's background work off is done by switching the login item off in System Settings or from the app, which unregisters the job; an exit never means "stay off".
- `ThrottleInterval` left at the default: launchd spawns a job at most once every 10 seconds and throttles one that exits quickly and often (same source). A crash loop therefore shows on the Health page as a restart count, never as a tight loop.
- `ProcessType` Adaptive, a `MachServices` entry for the XPC name the app connects to, and no `StartInterval`: launchd only starts and restarts the process; the runtime schedules its own work. `man launchd.plist` on macOS 27 says Background jobs get resource limits "intended to prevent them from disrupting the user experience", and that Adaptive jobs "move between the Background and Interactive classifications based on activity over XPC connections" (read during the design-skeptic pass). The same process serves the person's Approve clicks and the one-minute capture target, so the app wraps each request in an XPC transaction and the runtime stays Background the rest of the time. That means the digest runs under Background limits whenever the app is not talking to it, while every timing in 5.3 came from the `fm` tool in the foreground. Before release a spike measures, with the runtime classified Background, on battery, on a Mac that reports the 3B Core model: approval latency, the clerk's time per window, and the jitter of the 30-second beat (section 13, item 39 f). If the clerk always loses the race against the minute, every capture gets only a Tier 0 card, and the release notes must say so.

The app reads `SMAppService.status` and shows it in plain words: `enabled` is fine; `requiresApproval` shows a button that opens System Settings > General > Login Items (`openSystemSettingsLoginItems()`); `notRegistered` and `notFound` show a Register button (web-localfirst-platform). This is the first line of the Health page. When the person turned background work off on purpose, the app remembers that choice and shows a neutral "Background work is off (your choice)" with a Turn On button, never a red alarm.

Where the bundle runs from. A notarized DMG adds failure modes the research did not cover. The person may run the app from the disk image or from Downloads, where Gatekeeper may move a quarantined app to a randomized read-only path at launch (translocation). The person may also move the app to /Applications after registering, so the registered `BundleProgram` path is gone and the runtime is down with no signature failure. At every launch the app checks that it runs from its final location and is not translocated, and refuses to register from a disk image or a translocated path ("Move Sprava to Applications first"). It re-registers from its own path only when the registered path no longer exists and its own build is at least the registered build. Two copies of the app (one in /Applications, one left in Downloads) would otherwise flip the registration back and forth, restarting the runtime each time and sometimes running older code against the binders. In every other case of a path mismatch it shows "Another copy of Sprava is installed at <path>; use that one or remove it" and changes nothing. The doctor compares the registered helper path with the running bundle and reports every installed copy it finds.

### 3.2 The single-instance lease

On start, the runtime first checks that launchd started it for Sprava's label: it must check in its `MachServices` name successfully. A copy started by hand cannot, because only the launchd-managed instance can check in that name, and the app could never reach it over XPC. This comes from general platform knowledge, not from the research, and the XPC spike confirms it (section 13). Such a copy writes one line to `runtime/lease-refusals.log` and exits without touching the lease. A development build runs only with a `--dev` flag, which uses a separate Application Support folder and a separate socket, so the author's Xcode build never meets the installed app's data.

Then the runtime opens `runtime/lease` and takes `flock(LOCK_EX | LOCK_NB)`: an exclusive lock that fails at once with `EWOULDBLOCK` instead of waiting. The lock is advisory and bound to the open file; it vanishes when the process dies, so a crash never leaves a stale lease (web-localfirst-platform: `man 2 flock` on macOS 27.0; cmirror uses the same pattern). If the lock is held anyway (an old runtime still exiting after an update), the new copy appends "lease held by pid N" to `runtime/lease-refusals.log` and exits with status 0. Because `KeepAlive` is true, launchd starts it again after the 10-second throttle, and it takes the lease once the old copy quits. The Health page shows the refusals while they last.

This is the answer to "two copies of the sync loop ran for a week" (HANDOFF). Only a launchd-started runtime can hold the lease, so the copy that holds it is always the one the app can talk to. While it holds the lease, the runtime also removes a stale socket file left by a crash before it binds a new one (7.2).

Startup order. Lease first, then the heartbeat and the watchdog, then the persisted breaker states (3.4), and only then the startup reconcile of each binder (4.8), run as one job per binder with its own budget. A binder on a stuck volume or under a held lock is then named as a wedged job while the others proceed, and the runtime beats from its first seconds, even in a crash loop.

### 3.3 Heartbeat and watchdog

The heartbeat is driven by a plain repeating timer on the supervisor's own thread, every 30 seconds (proposed). It is not a discretionary background activity: `NSBackgroundActivityScheduler` lets the system defer work (web-localfirst-platform: its tolerance defaults to half the interval), and a deferred beat would raise a false "runtime stopped" alarm. On each tick the supervisor rewrites `runtime/heartbeat.json` atomically (a same-directory temp file, then fsync, which asks the disk to write out buffered data, then rename): pid, start time, beat time, last wake, build, XPC protocol version, the lease file's identity, model state, today's outbound counters, crash counts per stage, and for every job its last start, last success, expected cadence, last error code, consecutive failures, breaker state and whether it is wedged. The schema is in Appendix A. The app trusts the file only when it validates against that schema; a file that does not validate is shown as "health data unreadable", never as green.

The app shows the age of the last beat on the Shelf and the Health page. Under 2 minutes is green, from 2 minutes amber ("the runtime may be stuck"), and from 5 minutes red with a Restart button, which meets the success criterion that a stopped runtime is visible within five minutes (decisions.md M3). The Shelf badge takes the worst of the beat age and the job states (3.4), so a runtime that beats while one job does nothing is not green.

Sleep. Laptops sleep, and a heartbeat file is hours old after a night. The runtime beats at once on wake and records the wake time in the heartbeat. It learns of a wake through IOKit power notifications (`IORegisterForSystemPower`), the usual mechanism for a process with no window; whether `NSWorkspace.didWakeNotification` also reaches a background agent is not established, so it is only a second source. The app, which has a window, grades the beat age from the later of the last beat and its own last wake (`NSWorkspace.didWakeNotification`), and shows "waking up" for the first 60 seconds after a wake, never red. These facts come from general platform knowledge; the research did not cover them, and the delivery of wake and clock-change events to the agent is a spike (section 13, item 39 i).

Is the pid alive? The app checks that the recorded pid is alive, the combined rule holos uses for its recorder's status file (holos-formats). A pid can be reused after a reboot, so `kill(pid, 0)` alone is not enough: the app also checks that the process's start time equals the heartbeat's `started_at`, and that `started_at` is after the last boot.

Restart. The red state offers Restart, the person's only fix there. How Restart works is not established: the research documents `register()`, `unregister()` and the status values of `SMAppService`, but not that `register()` restarts a stuck process that is already enabled. The candidates are `unregister()` then `register()`, or `launchctl kickstart -k gui/<uid>/<label>`. A spike picks the one that works and this section records it (section 13). If a stale process still holds the lease, Restart offers to end it.

The watchdog covers what launchd cannot see: a process that is alive and stuck. A separate thread checks the tick counter every 60 seconds. It measures time with a clock that stops while the Mac sleeps (Swift's `SuspendingClock`, or `mach_absolute_time`), never wall time, so a night of sleep never looks like a stall. If no tick happened for 120 seconds of awake time (proposed), it writes one "stalled" line to `jobs.log` and exits with status 70, and launchd starts a fresh runtime. It does the same when any job has been marked wedged for 10 minutes (3.4), names that job as the culprit, and records the exit against that job in `runtime/breakers.json` before it exits (3.4). Jobs run as tasks under the supervisor and never on its thread. Blocking file and subprocess work runs on dedicated threads or in a subprocess, never on Swift's shared task threads, because a few blocked tasks there would stall every job while the beat continued.

Silence counts in both directions. If the app sees no beat, the runtime is presumed dead. If the runtime cannot write its heartbeat (disk full, permission lost), that is a failure of the heartbeat job, and it posts one notification, at most one per hour (proposed). Whether that notification can be posted at all is its own question (3.7).

The outside watcher. Only the app reads the heartbeat, and the app is an ordinary window that is often closed. The runtime cannot report its own death. So the bundle registers a second, tiny launchd job, `sprava-watch`. It is registered the same way as the runtime, from the same bundle, so it shares the runtime's fate in some failures. What it can and cannot see:

- It catches a crash loop (launchd keeps restarting the runtime and the beat never settles), a runtime that runs but whose heartbeat writer fails, and a hang the watchdog missed, while the jobs are still registered.
- It cannot catch a failure that takes it down too: the jobs unregistered, background work switched off in System Settings, or the bundle moved or damaged. Those are caught when the person next opens the app, through `SMAppService.status` and the bundle-path check (3.1), and, for a binder the hub reads, by the 7-day stale flag of `lifeproj brief` (section 11). launchd itself does not give up on a `KeepAlive` job: `man launchd.plist` says such a job is throttled, not abandoned (web-localfirst-platform).

The plist shape: `StartCalendarInterval` with four entries, `{Minute: 0}`, `{Minute: 15}`, `{Minute: 30}` and `{Minute: 45}`. `StartInterval` is not used, because `man launchd.plist` on macOS 27 says an interval that falls during sleep "will be missed due to shortcomings in kqueue(3)", while calendar firings missed during sleep are coalesced into one run on wake. That run happens at the moment of wake, when the beat is stale by the whole night, and possibly before the runtime has written its wake beat. So on each run the watcher:

1. reads `heartbeat.json` and checks that the recorded pid is alive and that its start time equals `started_at` (the rule of "Is the pid alive?" above);
2. grades the beat's age from the later of `beat_at` and the system's last wake time, read with `sysctl kern.waketime`;
3. if the last wake was less than 2 minutes ago, waits until 2 minutes have passed and reads the heartbeat again before deciding;
4. when the beat is still older than 15 minutes, the person did not turn background work off, and the app is not running, posts one notification: "Sprava's background work stopped 3 hours ago. Open Sprava to restart it." At most one a day.
5. writes the time it ran and what it saw to `runtime/watch.json`, its only write, which the Health page shows as "outside watcher last ran".

It holds no other logic. This is the "dead monitor nobody notices" lesson (HANDOFF). Whether switching off the login item in System Settings disables both jobs together is a spike (section 13, item 39 c).

### 3.4 The job list

Every job has a trigger, a budget, an idempotency rule, a list of what it writes, a breaker and an expected cadence. Two kinds of scheduling are used, and all cadences are proposed.

- Clock-time work (the sentinel at 00:05, the nudge job at 07:00, the daily summary at the person's chosen time) runs on wall-clock timers plus a wake handler (IOKit power notifications, 3.3), because a Mac asleep at midnight must catch up on wake. The runtime also re-arms these timers when the clock changes (`NSSystemClockDidChange`) or the time zone changes (`NSSystemTimeZoneDidChange`). Delivery of these to a background agent is part of the spike in 3.3; the hourly sentinel run limits the damage if one is missed.
- Discretionary work (backup, the weekly index rebuild, the doctor) is stated as "at most once per N hours, preferably at night". `NSBackgroundActivityScheduler` takes an interval and a tolerance, never a clock time (web-localfirst-platform), and laptops are usually asleep at night. So each such job keeps its own "due since" time, runs on wake when it is overdue, and asks the scheduler only for a good moment within its tolerance. `BGTaskScheduler` does not exist for native macOS apps (web-localfirst-platform: the SDK header marks it unavailable; decisions.md A1).

The one-minute target (decisions.md M3) is met whenever the runtime is up and the capture's file event arrives. M3 counts from the moment a capture lands, so the budget includes detection and the time it waits behind other captures. Landing is the event file's birth time on disk, or the time the producer renamed it into place when the producer records that. File events usually arrive within a second. When one is dropped (FSEvents can merge events or ask for a full rescan), the 15-second sweep finds the file, so detection takes at most about 15 seconds in that case. Each capture gets a deadline of its landing time plus 60 seconds. When its queue wait plus its estimated work would pass that deadline, the runtime files the Tier 0 proposal at once (section 5.2) and queues the clerk pass for later. Estimated work is the capture's windows and items times a moving median of recent call times for this Mac's model variant. When a clerk pass runs out of time, it never throws away finished windows: it publishes a partial proposal and lists the rest of the capture as unfiled spans (capture-event-v0 §6.4). The Health page and the 30-day measure report misses in three groups: captures that landed while the runtime was down or restarting, captures found only by the sweep, and captures the runtime saw in time but could not finish. Next to M3 it also shows a clerk measure: the share of captures that got a clerk reading within 5 minutes. For a multi-window capture the minute will often be met by a code-built card, and that measure keeps the clerk honest.

The retry policy, stated once here and cited by section 8. A capture whose clerk pass did not finish is retried once under a background budget of 5 minutes (proposed). What happens to the reading depends on what the person already did with the Tier 0 card:

- still undecided: the clerk's proposal supersedes the Tier 0 card;
- approved: the reading arrives as a change proposal against the item the person filed, for example "split this note into 3 items and drop the placeholder", marked "the clerk's reading of a note you already filed";
- rejected: the reading is not proposed again;
- if the retry fails too, the capture keeps its Tier 0 card and the Health page lists it as "the clerk could not read this".

The breaker threshold in the table counts consecutive failures across captures and is a separate thing.

Backfill. Events that the developer importer writes from history carry a backfill mark. They run at low priority, are excluded from the M3 measure, and the Health page says "importing 340 old captures" instead of turning the oldest-waiting line red.

The poison-input rule. One capture or catalog can crash the whole process: a model or framework crash, a parser bug. Text extraction runs in its own helper (2.1), so a PDF that crashes the extractor kills only the helper, and the runtime records a failed extraction and moves on. For what still runs in process, without a rule the journal would resume at the stage that crashed after every restart, every 10 seconds, and each loop would take down the heartbeat, MCP and every other job. So before a risky stage (a model call, parsing a catalog) the runtime records "attempt N started" and flushes it to disk: in `capture/journal.ndjson` for a capture, in `runtime/attempts.ndjson` for a catalog. Unfinished attempts also come from exits that are not crashes: a watchdog exit, the Restart button, an update, a power cut. So the runtime records the reason before every exit it controls (watchdog, SIGTERM, update), and those exits are not counted. On startup, an input with 2 unfinished attempts at the same stage and no recorded exit reason is not retried. A capture goes to the Tier 0 path. A catalog that crashed the parser twice sets that binder aside: the runtime stops reading it, never moves or changes the file (decisions.md F1), and shows "this binder could not be read". The Health page says "this capture crashed the clerk twice", and the heartbeat counts consecutive crashes per stage.

Rules that apply to every job:

- A job runs as a task with a deadline equal to its budget. Swift task cancellation is cooperative: a job blocked in a system call (a file in a cloud folder that is not downloaded yet, a stuck volume, a model call that ignores cancellation) does not stop when cancelled. So the scheduler never waits for a previous run before it records the overrun as a timeout. A task still running one grace period (proposed: equal to its budget) past its budget is marked "wedged" in the heartbeat, and the watchdog restarts the process when a job stays wedged for 10 minutes (3.3). For a subprocess such as cmirror or `age`, cancellation sends SIGTERM (a polite stop request), then SIGKILL (a forced stop) after 10 seconds (proposed).
- Breaker state survives a restart. Each job's breaker state, consecutive failures and watchdog exits are written atomically to `runtime/breakers.json` and reloaded at start. A watchdog exit caused by a job counts as a failure of that job, recorded before the exit (3.3). After 2 such exits the job's breaker opens, or the binder's breaker for per-binder work, and the rest of the runtime stays up. Without this, a job that wedges on every run (a binder on a stuck volume, a held lock) would restart the process every 10 minutes forever and interrupt every other job each time. The Health page says "restarted 3 times because of backup:b2".
- Each job declares its expected cadence. The app grades a job amber when the time since its last success passes twice its cadence and red at four times, so a job that never fails and never succeeds still shows. The time is counted from the latest of its last success, the last wake and the runtime's start, so a week with the lid closed does not paint every job red on wake. While overdue jobs run after a wake they show "catching up after sleep". A job may carry its own thresholds in the manifest; backup does (amber at 48 hours, red at 7 days; 9.3). A job whose cadence is "on demand" or "on event" is graded only by its errors.
- A job writes nothing partial. Every file goes through temp file, fsync, rename, directory fsync (holos-formats: the `AtomicFile` discipline in holos).
- A job that reads binders takes no locks on them. Binder writes are serialized by the guard inside the one runtime process, under each binder's lock (4.2).
- A job records start, end, duration and an error code in `jobs.log`, never binder content (3.7); the log rotates (2.3). The Health page shows the median and the slowest of the last twenty durations per job, so a slow job is named by a number before it is blamed by a feeling (HANDOFF "A slow hook was misdiagnosed").

### 3.5 Circuit breakers and timing

A breaker has three states. Closed: the job runs on schedule. Open: after the threshold of consecutive failures, the job is skipped and retried after a backoff of 1, 5, 15 and then 60 minutes (proposed). Half-open: one trial run; success closes the breaker, failure reopens it. The breaker state, when it opened, the last error code and the culprit (for the digest, which model call; for the watcher, which event id; for backup, which subprocess and which binder, by opaque id) are in the heartbeat and on the Health page. A breaker that opens posts one notification (3.7). Breaker state is persisted across restarts (3.4). The same timing and breaker wrapper applies to every hook or plugin added later (decisions.md A9), so nothing can hang for 30 seconds unseen. Sprava never executes hooks or scripts found inside a binder (decisions.md F9). What can be slow is Sprava's own code, cmirror, the model, the extraction helper, and the system calls Sprava makes: file reads on a slow or cloud-backed volume, a binder lock held by another program, Keychain calls, and XPC to the app. Each of those is timed and named too (2.1, 2.3, 4.1).

The wrapper also carries a budget counter for anything that talks to another service or a model: calls in the window, bytes out, and the reset time the service reported. A quota or authentication error opens the breaker with that reset time and is a visible error, never "0 done, 0 errors" (HANDOFF lesson). A run that did nothing is never a success. cmirror shows why this matters: when another run holds its lock, `cmirror backup` logs "another cmirror backup is already running" and exits 0 (cmirror `cli.py`), and the author already runs cmirror on its own schedule. So a backup counts as a success only when Sprava found the lock free just before the run, cmirror exited 0, and its output does not carry that skip message. One `cmirror` call over all projects also combines their exit codes (`_run_per_project`), so one broken binder would fail every binder; Sprava calls it once per binder with `--project`, with a breaker and a last success for each. A LaunchAgent does not inherit the shell's `PATH`, and cmirror finds `age` with `shutil.which` (cmirror `age.py`), so a Homebrew `age` would not be found. Sprava resolves absolute paths for `cmirror` and `age` at setup, shows them in Settings, and passes an explicit `PATH` to the subprocess; the doctor checks both. Model errors have their own counters (5.4), so "Apple Intelligence is off" shows as a model condition and not as a failing digest job.

### 3.7 What logs, errors and notifications may contain

Logs, error messages, notifications and the heartbeat never contain a binder title, a binder's folder name, an item title, capture text, document text, a capture or document file name, or a person's name. Folder names (`meta.name`) and file names are often as revealing as titles. They carry job names, codes, counts, durations, event and op ids, and an opaque binder id from `shelf.json`, never `meta.name`.

- The runtime logs through `os_log` and marks every string that could carry binder text as private, so the unified log redacts it. A build-time lint rejects any interpolation of a title or a name into a log call without `privacy: .private`.
- `jobs.log`, `lease-refusals.log` and the per-client MCP audit logs record names, times, sizes and error codes only.
- A macOS notification says only a count, such as "3 proposals waiting", "2 due today, 1 overdue, 3 to follow up" or "Backup has not run for 3 days", because notifications can appear on a locked screen.
- Every alarm raised while the app is closed is a notification, so notifications are a component that can fail silently too. The research does not show that a helper executable inside the bundle (the runtime or `sprava-watch`) can post notifications under the app's identity, or what it sees when the person denied permission or a Focus mode hides them. That is a spike (section 13, item 39 h). The runtime reads the notification authorization status at start and every hour and puts it in the heartbeat; when alerts are off, the Health page shows the red line "Alerts are off: Sprava cannot warn you when it stops". A notification that could not be posted counts as an error on the job that tried to post it.
- Crash, assertion and precondition messages never contain binder content, because macOS may send crash diagnostics to Apple when the person shares Mac analytics (section 10).
- The doctor searches Sprava's own files (`jobs.log`, `lease-refusals.log`, the audit logs, the heartbeat and `doctor.json`) for every binder's title, every `meta.name` and every open item's title, and reports any hit as a finding (section 12). It does not search the unified log: private strings are already redacted there, and reading the system log store from an ordinary process is restricted. Both points are unverified.

## 4. The op log and the transaction guard

This section defends the "one gate" principle and the "Sprava's own bugs" row of the threat model. Decision F1 fixes the shape: the catalog is the truth of state, the op log is the truth of history, every op records the catalog's content hash before and after, and Sprava adopts a binder in place (decisions.md F1, A2). The exact op vocabulary, the write protocol and their JSON Schemas are in `docs/spec/teka-v0.md` §4.9, §6 and §10; this section describes the mechanism and does not restate the format.

### 4.1 The record

`.sprava/ops.ndjson` holds one applied op per line, append-only (teka-v0 §6.2, §6.9). A line holds:

- `id`, a UUID (a random unique identifier; version 7 recommended because it sorts by time), and `at`, the time it was applied.
- `actor`: who caused it. `user` (the person, acting in the app), `clerk` (Tier 1), `brain` (Tier 2; teka-v0's `actor.client` names the implementation that applied the op, so the MCP client's name needs a field of its own, section 13, item 10), `import` (adoption, migration and crash recovery), or `external` (a change made outside Sprava and detected afterwards, including completions drained from the hub's outbox).
- `proposal` and `approved_by` when the op came through the review queue; both are required for clerk and brain ops. `batch`, `seq` and `batch_size` group and order the ops applied together.
- `op` and `args`: the typed change, such as `add_item`, `update_item`, `set_status`, `complete`, `drop`, `reopen`, `dismiss`, `file_document`, `set_disclosure`, `external_edit`, `import_snapshot` or `migrate`, plus two runtime records this design adds, `takeover` (2.3) and `rekey` (below), which ask for a teka-v0 change (section 13, item 10). Every input to an op's effect is in the line: `at` stands for "today", and `args` carry any computed value, such as a recurring item's next due date and the timestamps. Re-applying a line therefore never reads the clock.
- `before_hash` and `after_hash`: a SHA-256 hash (a fingerprint of the content) of the whole catalog in RFC 8785 canonical form (one fixed way to write JSON, so the same content always gives the same fingerprint) before and after this op (decisions.md F1, F10). `after_hash` of one line must equal `before_hash` of the next. That is the chain. Hashes are per op, never per batch.
- `seal`: a keyed hash (HMAC-SHA256) made with a runtime key kept in the Keychain, out of the shim's reach. It covers the line, the binder's id, a key id and the previous line's seal, so a sealed line cannot be copied into another binder, and removing or reordering lines breaks every later seal. The seal carries the key id in the clear. Other implementations ignore the field (teka-v0 allows unknown fields on op lines).
- `compensates`: on an undo, the id of the op it reverses.
- `hlc` (a hybrid logical clock stamp: wall time plus a counter plus a device id) is reserved for merging logs from several devices later; it is not needed on one Mac (decisions.md C1).

What the chain proves. A plain hash chain can be recomputed by anyone. It detects accidents: a hand edit, a lifeproj drain, a terminal agent's digest, a bug. It does not detect forgery. A process that appends consistent lines claiming `actor: user` and then rewrites the catalog would pass the chain. The seal is what gives attribution: a line without a valid seal is treated as part of an external edit, and history never shows it as a change the person approved. A writer could also cut lines off the end of the log and put the catalog back to an earlier state; the chain would still look whole. So `shelf.json` (sealed) keeps a high-water mark per binder: the last op id, the line count and the head seal. A log shorter than that mark raises "history went backwards" (4.5).

Key changes. When the key changes (a restored or new Mac, or a lost Keychain item), the runtime appends a sealed `rekey` checkpoint under the new key that records the head hash, the line count and the old key id. Lines before the checkpoint that verified under the old key are shown as "sealed by an earlier key". Lines after it must verify under the current key. A line with a bad seal anywhere is an external edit, so old history cannot be rewritten under cover of a rekey.

When the key cannot be read. The guard needs the key for every op. The runtime reads it once at start, with no user interface allowed, and keeps it in memory. If the read fails (the keychain is locked, its password no longer matches the login password, a background agent gets an "interaction not allowed" error, or the item is gone), the runtime runs read-only: it queues writes, never writes an unsealed line, and the Health page says "Keychain locked: approvals paused". It never creates a new key on its own; a new key is created only after the person confirms it on a card, which then appends the `rekey` checkpoint. The item's class must be readable while the screen is locked, because the 3 a.m. jobs write sealed lines: a data-protection keychain item, not synchronized, readable after first unlock on this device only. None of this is in the research, so it is spike (g) of section 13, item 39.

Hashing the canonical form matters for coexistence. lifeproj rewrites a catalog with `\uXXXX` escapes for non-ASCII text after its first drain, and editors and agents re-indent files (lifeproj-schema). A pure reformat changes the bytes and not the content, so it records nothing. When lifeproj does drain a completion, the external-edit patch holds only the closure, never escaping or indentation noise. lifeproj writes `catalog.json` only when it applied something (`osavul.py`, `_drain_teka`), so a drain that applied nothing never touches the file.

### 4.2 Applying a batch

The guard is the only code path in Sprava that writes `catalog.json`. It works on one binder at a time, inside the one runtime process, and follows the write protocol of teka-v0 §4.9, which every writer of a binder follows, lifeproj included once it changes (teka-v0 §9.8).

1. Take the binder's lock: an exclusive `flock` on `.teka.lock` with `LOCK_NB`, retried for at most 10 seconds (proposed), held until the last step and never while waiting for the person. A lock still held after that puts the binder in the "busy" state of 2.3; no thread ever blocks on `flock`.
2. Load `catalog.json` and hash it. Compare with the last `after_hash` in the log. On a mismatch, absorb the external edit first (4.5).
3. Check idempotency: an op or proposal id already in the log is a no-op that returns success.
4. Check that the proposal is one the runtime wrote or received over MCP, that its approval arrived over XPC from the app, and that three digests agree: the one the runtime recorded when it stored the proposal, the one of the file as it is now, and the one of the card the person approved (4.6). Check its `expect` fingerprints against the current items. A mismatch stops here and the card shows "needs a look", or "proposal changed outside Sprava" for a digest mismatch.
5. Mint ids. A proposal names new items with placeholders such as `$new:1`; the guard replaces each with a real id now, by the minting rule of teka-v0 §5.6, and later ops in the batch resolve the placeholders. Ids are never fixed at proposal time, so a terminal digest that takes the next number in the meantime cannot make the approval fail.
6. Apply the batch's ops in order to an in-memory copy, computing each op's `after_hash`, and run the transaction guard of teka-v0 §6.3: the batch is accepted when it adds no new violation and every record it creates or changes is valid afterwards (decisions.md F2, F3). A batch applies whole or not at all: if any op fails, nothing is written and the card shows the reason in plain words. Every string the batch stores, from any actor, passes through one sanitizer in the guard: it removes control characters, Unicode TAG-block characters (U+E0000 to U+E007F), bidirectional overrides, zero-width characters and other default-ignorable code points, and the card flags each removal (6.1). Text stored in `catalog.json` reaches terminal agents through the file and `DASHBOARD.md`, which Sprava does not otherwise sanitize for.
7. Write the new catalog to a temporary file in the same folder, created exclusively under a name with a fixed pattern, `.catalog.json.sprava-<random>.tmp`, so leftovers can be found. The name starts with a dot and ends with `.tmp`, as teka-v0 §3.6 requires. Then read `catalog.json` again and hash it. If the hash differs from step 2, someone wrote the file without the lock: delete the temporary file and go back to step 2, still holding the lock. The outside write is then recorded as an external edit. This narrows the window for programs that skip the lock, such as a person in a text editor or today's lifeproj. It cannot close it.
8. Append the batch's lines to `ops.ndjson` in one write with `O_APPEND` (the open mode that always writes at the end of the file), then flush to the drive. Plain `fsync` on macOS does not force the drive to flush; `F_FULLFSYNC` does (web-localfirst-platform: `man 2 fsync` on macOS 27), so the guard uses it for the log and the catalog. If the write fails, the file is truncated back to its recorded size, so a partial line never survives (holos-formats: the append discipline in holos).
9. Hash `catalog.json` once more, because the log flush in step 8 is the slowest step and widens the window. If it changed, append an `abort` for the batch, delete the temporary file and go back to step 2. Otherwise rename the temporary file over `catalog.json`, `F_FULLFSYNC` the folder, update `.sprava/snapshot.json` and the binder's high-water mark (4.1), and release the lock. Key order and formatting follow decisions.md F10.
10. Mark the proposal `applied`, regenerate `DASHBOARD.md`, update the index, mark the slice for republishing, and tell the app. These derived files need no full flush because they can be rebuilt.

A batch with more than one op always comes from a proposal file, which lists its ops; a direct action by the person is a batch of one. Each line carries `batch_size`, so after a crash the guard knows what a complete batch looks like. On startup, for every binder, recovery follows teka-v0 §6.7 and §6.9:

- The catalog hash equals the last `after_hash`: all is well. If the proposal is still marked `approved`, mark it `applied`.
- The catalog hash equals the `before_hash` of the first line of the last batch, and the batch is complete: the catalog write did not happen. Roll it forward by applying the logged lines again; every input is in the lines (4.1), so each hash must match. Roll forward runs only for a batch whose lines carry a valid seal and whose approval came over XPC (4.6), never on the strength of a proposal file's `state`.
- The last batch is incomplete, or a torn last line: it never took effect. Its lines are copied to `.sprava/torn/` and truncated before the next append (teka-v0 §6.9), and its proposal goes back to `proposed` for the person to approve again.
- Neither: an outside program wrote the catalog after the crash. The guard first tests whether the found catalog descends from the last state that reached the disk (`.sprava/snapshot.json`, which is updated only after a successful catalog write). Ops logged after that state never took effect, so an `abort` names them first. Then the outside change is recorded as an external edit from that state (4.5), never from a state the catalog did not reach. The proposal of the aborted batch returns to the queue, is re-checked against its `expect`, and is applied again or shown as "needs a look". Approved changes are never silently lost.

A torn last line (no trailing newline) is copied to `.sprava/torn/<timestamp>.ndjson` and truncated away before anything else happens, which is what holos does with its journals (holos-formats; teka-v0 §6.9). Each torn tail is a doctor finding. Leftover temporary files matching `.catalog.json.sprava-*.tmp`, from a crash between steps 7 and 9, are deleted under the lock in the same pass and counted as a doctor finding, so they never pile up where lifeproj, terminal agents and Spotlight see them.

GTD contexts (from the Getting Things Done method: `@`-tags that say where or with what an item can be done) resolve in the hub's order: an explicit tag on the item, then the binder's default (`meta.default_context`, proposed in teka-v0 §12), then `@anywhere`. While the hub owns them, Sprava shows its own binder fields for these but does not offer them on the Today page. The hand-over is an explicit export: the hub writes its annotations for that binder into the spool, or the person copies them by hand, and Sprava offers them once as an import proposal. Sprava never reads the hub's files. This refines decisions.md A8 (section 13).

### 4.4 Undo

Nothing is ever removed from the log. Undo appends a compensating op that names the original in `compensates` (decisions.md A2, A5; web-localfirst-platform: the event-sourcing rule that history is corrected only by compensating events). The table of inverses is teka-v0 §6.10. In short: the inverse of `add_item` is `drop` with the reason `undo`; of `update_item`, an `update_item` with the previous values, which the log holds; of `set_status`, the previous status; of `dismiss`, `undismiss`. A closure cannot be taken back in place, because its entry in `processing_log[]` is append-only and a closed id is never reused (decisions.md F2). lifeproj's checker reports an open item whose id is in the log as "reused", and `lifeproj publish` then refuses the whole slice. So undo of `complete` or `drop` is `reopen`: the item comes back under a new id, its fields copied from the closure entry, with `provenance.reopened_from` pointing at the old id. Undo of a recurring completion sets `due` back with `update_item`; the occurrence entry stays as history beside the undo. A filed document is never deleted; its record can be corrected with `update_document`. The app's Undo button is only a shortcut to the compensating op, and the item's history offers Undo at any time. Undo of a completion that came from the hub reopens the item under its new id; the hub sees a new item in the next slice, and the old id stays closed. How a closure reaches the hub before the v1 `closed[]` field is switched on is in section 11 (teka-v0 §6.10).

### 4.5 External edits

An external edit is any change to `catalog.json` that did not go through the guard: a hand edit, a lifeproj drain, a terminal agent's digest. It is expected, because lifeproj is a second implementation of the same format (decisions.md F1).

Detection happens on every read of the catalog, which includes every job that touches a binder and every MCP read, as well as on writes (decisions.md A2). When the hash does not match the last `after_hash`, the guard follows teka-v0 §6.7 under the binder's lock:

1. Compute an RFC 6902 JSON Patch (a list of add, remove and replace steps) from the expected catalog (`.sprava/snapshot.json`, or a replay of the log) to the catalog as found.
2. Append an `external_edit` op holding the patch, with `before_hash` equal to the expected state's hash and `after_hash` equal to the found hash, and a `hint` when the editor is obvious (a new closure entry whose `via` is `lifeproj drain`; lifeproj-schema). The Shelf shows "edited outside Sprava" on the binder for a day.
3. Check whether the edit undid approved work. An editor or script that held an old copy of the catalog, for example a file the person opened before Sprava applied a capture and saved after, lands between two of Sprava's writes. The chain sees it, but the patch silently removes items or values the person approved, while the queue still shows those proposals as applied. So the guard compares the patch with the ops applied since the previous external edit. When the patch removes or reverts values those ops set, the person gets a card: "An outside edit undid 3 changes you approved", with one click to apply them again, rebuilt from the logged ops and passed through the guard as a new batch. The count is on the Health page.
4. Validate the found catalog, in two parts, because terminal agents follow a manual that knows lifeproj's rules and not the v0 additions (decisions.md F1 keeps that manual unedited):
   - A record that breaks lifeproj's v2 rules, which terminal agents know (decisions.md F2), puts that record in "needs attention" (teka-v0 §9.6). Ops that touch it are refused; other items, other ops and the outbox drain still apply. The dashboard is regenerated with a warning, and a repair arrives as a proposal (for example "add `no_deadline: true` to an item that has neither a due date nor `no_deadline`").
   - A record that misses only a v0 addition blocks nothing, and its repair follows teka-v0 §6.7: it is offered, never written straight away. A missing `kind` on a redacted item, or an item set to `status: done` (repaired as a `complete`), is a card. Purely mechanical repairs, such as a missing `follow_up_at` on a waiting item derived as decisions.md F3 says, wait until the catalog has had no outside write for a quiet period (proposed: 10 minutes) and are then applied as one undoable `import` batch. A terminal agent is often in the middle of a digest when Sprava sees its edit, and a write from Sprava at that moment makes the agent's next edit fail ("modified since read") every time it sets an item to waiting.
5. Apply the privacy ratchet. An outside edit can raise `meta.disclosure`, clear `redact`, remove `slice_title`, or remove or lower `documents[].sensitivity` (7.3). A narrowing change takes effect at once. A widening one does not: every cross-binder surface (the slice, MCP, the Today page) keeps projecting with the last value the person confirmed in the app, until the person approves a privacy card for it. The confirmed values live outside the binder, in the sealed `shelf.json`: each binder's disclosure and, per item and per document, the confirmed `redact`, `slice_title` and `sensitivity`. A binder's own log cannot be the source, because its tail can be cut off (4.1). When the log is shorter than the binder's high-water mark, the person gets a "history went backwards" card, and every surface projects with the narrower of the stored and the found values. A legitimate restore looks the same and is confirmed on the same card (section 8). The same rule holds for a change that adds a binder to a brain's scope (7.5). So a hand edit or a terminal agent can never widen what leaves the binder without the person seeing it.

What the chain catches, and what it does not. Sprava takes the binder's lock (4.2), and lifeproj will take it once it changes (teka-v0 §9.8). A text editor and today's lifeproj take no lock. The chain detects an outside write that lands between two of Sprava's writes. It cannot detect a lost update inside one write: if an outside program writes the catalog after the guard read it and before the guard renamed its own version, and the guard's rename then replaced it, the catalog ends exactly at the guard's `after_hash` and nothing looks wrong. The compares before rename (4.2 steps 7 and 9) narrow that window to the moment between the last hash and the rename, which no longer includes the log flush. They do not close it. For a person typing in an editor that remaining risk is accepted (section 13). For lifeproj's scheduled drain it is not, which is why a managed binder has one drainer and one publisher (section 11).

### 4.6 Proposals

A proposal is a file in `.sprava/proposals/<id>.json`, or in `unfiled/` while its binder is "not sure" (teka-v0 §6.5). It holds a header (`id`, `created_at`, `actor`, `state`, a one-line `title`, a `confidence` from 0 to 1, and `provenance`: the capture event ids, the interpretation id, and the producer with its tier, model, variant, OS build and prompt version, or the brain's client name) and the op bodies, each with its own confidence and the spans of source text it came from. New items in a proposal carry placeholder ids, never real ones (4.2 step 5); `propose_ops` rejects ids that a client supplies for `add_item`. A producer never applies its own proposal.

Confidence is computed by code, never written by a model or a brain. Apple's API gives no token probabilities, and in the 2026-10-06 runs the model gave binder confidence 1 to wrong binders as readily as to right ones (capture-event-v0 §6.4 check 5, §10.5). The signals are concrete checks: every quote anchored, every date resolved, no number or time word in the sentence missing from the item, agreement with `binder_hint`, an index match of the sentence in the binder, and agreement with neighbouring items. Any confidence a brain sends is ignored. The number is advisory and code never acts on it alone (capture-event-v0 §6.4 check 5).

Files are not trusted. Proposal files sit in a folder that any program running as the person can write, a brain with file tools included (7.7). Knowing a proposal's id is not enough: a writer could keep the id and rewrite the ops inside, and the person would approve one thing while another was applied. So:

- When the runtime creates a proposal, or receives one over MCP, it records the SHA-256 of the proposal's canonical body (RFC 8785, as for catalogs) in a sealed journal entry. Op-log lines exist only after apply, so they cannot cover a pending proposal.
- The app gets each card's content from the runtime over XPC, never from the file alone (2.1).
- The Approve message carries the digest of the card the person saw. An Edit sends the edited ops themselves over XPC.
- The guard applies only when the recorded digest, the file's current digest and the approved digest all match (4.2 step 4). On a mismatch the card says "proposal changed outside Sprava" and nothing is applied.
- A proposal file the runtime did not write is ignored and listed on the Health page as "unknown proposal file". A proposal file's `state` never approves anything; approval arrives only over XPC from the app (2.1).

A brain's document stays inside its proposal. Its body is held in `.sprava/proposals/<id>/` until approval, and nothing reaches the binder's visible folders before then (7.3).

Each proposal also carries `expect`: the values it assumed about the existing items it touches, for example `{"kitchen-reno-2026-014": {"status": "open", "due": "2026-10-20"}}`. At approval the guard compares them with the current items. Any mismatch marks the card "needs a look" with a short diff, and nothing is applied until the person looks. holos uses the same rule for its speaker edits: each edit carries an `expected` fingerprint of the prior value, and a mismatch makes the edit stale (holos-formats). This is item-level staleness. A change elsewhere in the binder does not disturb a proposal that does not depend on it.

States follow teka-v0 §6.5: `proposed`, `approved` (brief, while the guard applies it), `applied`, `rejected`, `superseded`. Two Sprava rules sit on top:

- A brain may withdraw its own pending proposal. Until teka-v0 has a `withdrawn` state, a withdrawal is recorded as `rejected` with the reason "withdrawn by <client>" (13).
- A proposal untouched for 30 days moves to a "Later" tab and stays `proposed`. Nothing is deleted while it waits; how long a rejected proposal is kept is teka-v0's question (teka-v0 §6.5, §12).

A proposal whose source capture is replaced by a newer capture event from the same registered producer (decisions.md C1; section 8) is superseded, and the new capture produces a fresh proposal. When that would discard a pending proposal the person may already have looked at, the replacement is shown as a card ("this note was corrected; review the new reading"), never as a silent swap. Proposals are idempotent by id, and `propose_ops` over MCP is idempotent by the client's request id.

### 4.7 Adoption and migration ops

Format changes are ops too, and adoption follows teka-v0 §9.4. It takes the lock, copies the `DASHBOARD.md` it found to `.sprava/adopted/DASHBOARD.md`, and appends an `import_snapshot` op holding the catalog as found and a structure survey. In a lifeproj binder the dashboard is written by an agent or a bespoke script and may hold text that cannot be derived from the catalog (lifeproj-schema: lifeproj has no renderer), so it is kept before anything else happens. Sprava then regenerates `DASHBOARD.md` only when the person accepts the switch on a one-time card that says the old dashboard was kept (teka-v0 §7.1). After the switch the unedited manual still tells terminal agents to rewrite the dashboard at each digest, so every render follows teka-v0 §7.1 exactly: the file starts with the marker line and the hash of the rest; before each render the renderer checks the marker, and when the file was edited outside the `## Notes` section it first saves it as `.sprava/adopted/DASHBOARD-<timestamp>.md` and says so; everything under `## Notes` is carried into each new rendering. The paste-in section for the manual tells agents to write only under `## Notes` (section 12). The doctor also reports when an outside tool rewrote `DASHBOARD.md` since the last regeneration.

Mechanical, lossless additions follow as `import` ops without a proposal, each marked derived, and are shown together on one card the person can undo: for example a `follow_up_at` derived from the due date of each waiting item (decisions.md F3). Everything that changes meaning goes to the queue as proposals: closing an item that sits in `open_items[]` with `status: done`, asking for a date or `no_deadline` on an item that has neither, completing document records. The person is asked to set `disclosure`. When every item satisfies the v0 rules, a `migrate` op stamps `format: "teka"` and `format_version: "0"` beside the existing `schema_version` (decisions.md F6). A lifeproj `schema_version: 1` catalog is reported as "needs migration", never as corruption (lifeproj-schema: three checker generations exist and nothing migrates).

### 4.8 Crash safety summary

- Every write is atomic: temp, flush, rename, folder flush.
- Every catalog write happens under the binder's lock, taken without blocking, with two compares before the rename.
- The op log is written ahead of the catalog and flushed with `F_FULLFSYNC`; everything else is rebuildable, apart from proposals, `captures/`, `.sprava/slice-key` and `.sprava/adopted/`.
- Startup reconciles each binder in one pass, after the lease, the heartbeat and the watchdog are running, as one job per binder with its own budget (3.2): torn-tail repair, leftover temporary files, chain and seal check against the high-water mark, roll forward or abort, external edit, proposal states and digests, index freshness.
- Ops are idempotent by id, proposals by id, capture processing by event id and stage, with an attempt count per stage.
- Batches apply whole or not at all.
- Inside Sprava there is one writer. Outside it, the lock is the agreement every writer keeps, and the compare before rename protects against those that do not yet keep it (4.5).

## 5. The tiers under the budget

This section defends boundary 4. The on-device model is small, and the design treats its context window as a hard budget.

### 5.1 The budget

The clerk is designed for 4,096 tokens and reads `SystemLanguageModel.contextSize` at runtime (decisions.md P2). The 8,192-token window belongs to the "AFM 3 Core Advanced" model on Macs with M3 or later and at least 12 GB of memory; the 3B "AFM 3 Core" model on M1 and M2 Macs keeps 4,096 (web-apple-fm: Apple staff in developer forum threads 832555 and 843063, Apple support page 127893, the WWDC26 session 319 code sample; measured as 8,192 on the author's M5 Mac). The 4,096 figure for M1 and M2 has not been measured on hardware (web-apple-fm, gaps), which is why the design budgets for 4,096. The variant follows memory as well as the chip: Core Advanced needs "Mac models with M3 and later and at least 12GB of unified memory" (web-apple-fm: Apple support page 121115), so an M3 or later Mac with 8 GB also runs the 3B Core model. This design therefore speaks of "a Mac that reports the Core model and 4,096 tokens", never of "M1 or M2". decisions.md P2 words it by chip, a small refinement listed in section 13 (item 23). The window is shared between input and output. Overflow throws `contextSizeExceeded`, carrying `contextSize` and `tokenCount`. A session answers one prompt at a time; a second prompt while one is running throws `concurrentRequests` (web-apple-fm).

Apple's guidance shapes every call: one specific task per prompt, one to three paragraphs, split work across sessions, let code do math and dates, keep instructions free of untrusted content, use greedy sampling for classification, and re-test prompts on each model version, because the 26.0 to 26.3, 26.4 and 27.0 models behave differently (web-apple-fm: Apple's prompting and context-window documentation and WWDC25 session 248).

### 5.2 Tier 0, the organizer

Everything below runs with no model and must be correct without one: the buckets Overdue (open items only), Today, Next 7 days, Later, No deadline, Nudge (waiting or blocked with `follow_up_at` today or earlier), Waiting and Recently closed (decisions.md F4); recurrence (decisions.md F3, the hub's rules in 4.3); GTD contexts (4.3); the roll-up with per-binder staleness; adopt-in-place; the slice and outbox; backup; the index; the doctor.

Tier 0 also has a capture path. When the model is unavailable (`deviceNotEligible`, `appleIntelligenceNotEnabled`, `modelNotReady`), when the capture's locale is unsupported, when the digest's breaker is open, when a capture would miss its one-minute deadline (3.4), or when an input crashed the clerk twice (3.4), code still builds a proposal: one item whose title is the capture's first sentence (cut at 120 characters, proposed), binder "not sure" unless the event carries a `binder_hint` that section 8 honours, no dates, and the full text attached. The card says "filed by code, no model" and the person files it by hand. The proposal's actor is `clerk` with no model, and its producer records tier 0 (capture-event-v0 §6.2). Captures never just wait while Apple Intelligence is off. The product works without it; it is only less helpful.

### 5.3 Tier 1, the call plan

The clerk works on one capture at a time plus a few retrieved facts (HANDOFF "Constraints"). The call plan, the windows and the code checks belong to capture-event-v0 §6.4, and this section follows it. This section owns the token table, the time budget and what happens when time runs out. In short, each capture is read in three kinds of call, each a small task in its own session:

1. Extraction. Code splits the capture into windows of about 100 to 150 words at paragraph boundaries, or at turn boundaries for a meeting. One call per window lists the items, each with its title, action, time words, people, amount words, and the opening words of its sentence as a quote. This call carries no binder list, no retrieved facts and no binder content. The published model schema allows at most six items per window (`maxItems`).
2. Binder. One call per item (and one per document) picks the binder from a closed list: an enum of the names offered plus `not-sure`, each name with a one-line description. The call gets the item's sentence and the window's opening sentence, because an item's own sentence often lacks the context: in one measured run the model chose a `small-business` binder for "the plumber sent his invoice", whose binder, `rental-elm-street`, was named only in an earlier sentence. When the capture carries a `binder_hint` that section 8 honours, code takes that binder and skips this call. capture-event-v0 §10.5 measured the combined call (split and pick in one): of 16 items, 7 were right, 1 wrong and 8 not sure, which is why the binder is its own call.
3. Duplicates. Only for an item whose binder's index returns candidates, one call answers which candidate it is (or `none`) and how it relates: `same`, `done`, `update` or `related` (section 8, step 4).

Plain code finds each quoted sentence, resolves dates from the capture's own timestamp and locale (decisions.md A3; capture-event-v0 §6.6), computes amounts and confidence, assembles the interpretation (decisions.md C3) and builds the proposal. Documents use the document call, one per short document, followed by one binder call (decisions.md P5).

Why windows and not one long call. The first draft of this plan read a capture of up to about 1,200 words in one call with an 800-token answer cap. The first design-skeptic pass measured that answers grow with the input, at 1.6 to 1.85 answer tokens per input token, with `fm respond --save-transcript` and `fm count-tokens --transcript` on invented dictations (macOS 27.0 build 26A428, Apple M5, Core Advanced model, 8,192 tokens). A 327-word dictation gave 12 items in 626 answer tokens, 1,361 tokens for the whole session, in 13.2 s. A 639-word dictation gave 23 items in 1,325 answer tokens, 2,411 for the session, in 29.0 s. capture-event-v0 §10.5 found the same independently: 538 words gave a 1,271-token answer in 40.9 s and missed 7 of 18 items. So the window size stays fixed, and on a Mac reporting 8,192 tokens it does not grow, because recall falls as the window grows.

The budget per call. All figures are tokens, measured on 2026-10-06 on invented text with the `fm` developer tool. `fm` is a measuring tool only (decisions.md P3), and its JSON-schema path is not the product's `GenerationSchema`, so in the product the clerk measures every part with `tokenCount(for:)` before each call. Schemas were counted as their minified published JSON, which a saved session transcript confirmed for the capture schema (412 tokens); rows marked "proxy" have no published model schema yet. Instructions are realistic ones: field rules, the capture date and weekday, the locale, the rule that the note is data, and the explicit "You MUST respond in French" line Apple recommends. Framing, the overhead a session adds, was measured at 54 tokens (web-apple-fm reports 55 to 60).

Tokens per word differ by language: about 1.22 for English and 1.43 for French on the windows above. A cap stated in words would be about 17 percent too generous for French (decisions.md P8), so every cap here is in tokens.

On a 4,096-token Mac every call fits with more than 2,400 tokens to spare. The token budget is therefore not the binding limit. Recall, the six-item cap per window and runaway answers are, and the rules below are about those.

Rules that make the table hold:

- Before every call the runtime measures instructions, schema and input with `tokenCount(for:)`, adds an answer reserve of min(6, expected items) x 110 tokens plus a margin, and checks that the sum fits `contextSize` (decisions.md P2). Expected items come from code's count of sentences that hold an action verb, a time expression or an amount, capped at six because the schema returns no more. When the sum does not fit, code makes the window smaller. `maximumResponseTokens` is set to the reserve.
- Six is a ceiling, not a count. In two measured runs, one English and one French window of about 140 words, each holding about nine things to do, came back with exactly six items. Both dropped the accountant follow-up ("next week ... if not I'll chase him on the 20th"), both folded "pay the plumber" into "check the invoice", and the French run lost "le 30 octobre" from the tax item. One sentence often holds two actions (capture-event-v0 §6.4 check 6), so a sentence count is not an upper bound. So when a window returns exactly six items, code splits it in half and runs both halves again, once. A window that cannot be split (one long sentence) gets the card flag "the clerk may have missed items here". Either way the coverage check (capture-event-v0 §6.4 check 9) lists what is left as unfiled, in the capture's own words.
- Window size is a starting point. It is set per locale from measured item density on the fixtures; dense dictation may need windows of 75 to 100 words.
- A cut-off answer keeps its finished items. Code streams the response and keeps the items that were complete when the reserve was reached, as capture-event-v0 §6.4 says; the rest of the window goes on the card as an unfiled span with reason `truncated`, and the derived event's outcome is `partial` (capture-event-v0 §6.3). Whether a streamed guided response gives complete items at the cap is not in the research, so it is a spike (section 13, item 39 j): it records what the framework returns or throws when it reaches `maximumResponseTokens` under guided generation, streamed and not. If streaming cannot deliver complete items, the clerk uses a single response instead, and a cut-off window becomes a whole unfiled span that is retried once at half size. Both documents will say the same once the spike settles it.
- The model writes only the opening words of each sentence as its quote, at most twelve words, and code finds the whole sentence, because quotes were the largest part of the answer. In the six-item runs the answer was about 50 to 55 tokens per item, so the 110-token reserve is safe.
- Every field the model fills is required and may be empty. In the samples the model left out optional fields or filled them with sentinels such as an amount of 0 with the text "none" (capture-event-v0 §10.5). Code turns empty values into absent fields before validating against `interpretation.schema.json`. Because `minLength` and `maxLength` are not enforced under guided generation (capture-event-v0 §6.4), code also guards every field's length while the answer streams and stops the call when one runs away.
- On `contextSizeExceeded` the window is halved and the call retried once; a second failure puts that window's text on the card as an unfiled span. The other windows' items stand.
- Greedy sampling for every clerk call. Every measured run used greedy sampling, and two greedy runs gave identical content (capture-event-v0 §10.5). Default sampling would make fixtures, the per-model re-tests and "why does it say that" impossible to reproduce.

The document call. The model reads only the first block of the document, about 400 tokens: the letterhead, the date, the parties and the first paragraph. Code's date grammar and amount parser scan the whole text for deadlines and amounts, and code adds them to the card as found by code. The reason is measured. One greedy run with the published document schema on an invented one-page contractor invoice (752 tokens of text, 12 line items, payment terms) ran for 169 s and then failed with "The session's transcript exceeded the model's context size" on the 8,192-token Mac: the input was about 1,450 tokens, so the answer ran past about 6,700. The same invoice cut to its header and payment terms answered in 4.0 s with the right date, kind, parties and three deadlines. Halving the input on `contextSizeExceeded` does nothing for a runaway answer; the first-block rule, the field-length guard and the reserve do. Itemized invoices join the fixtures, and the call is measured again on the 3B model.

Meetings. A one-hour meeting is roughly 8,000 to 9,000 words (an estimate, at 130 to 150 spoken words a minute): 55 to 90 windows, or 6 to 11 minutes of extraction alone on the M5 before any binder or duplicate call, and longer on the 3B model. The clerk is good at captures and short documents and poor at long ones (kickoff summary, point 3), and decisions.md P5 limits Tier 1 to one capture or one short document. So the clerk's work on a meeting is bounded:

- When holos supplies action items, the clerk reads each action item with the turns it quotes, one item at a time, as capture-event-v0 §12 question 6 offers as its second option. holos's own summary and key points arrive as derived events with `producer: holos` (decisions.md C4) and are shown on the card; they are not interpreted again.
- Without action items, the clerk reads the first 6 windows (proposed) and marks the outcome `partial`.
- The transcript is filed as a document of the meeting (section 8), and the card offers the full reading to a connected brain (Tier 2).
- Model work is scheduled round-robin by capture, so a meeting never makes a dictation that lands meanwhile wait behind it (3.4).

On the M5, a meeting with 15 action items then costs about 15 short reading calls plus 15 binder calls and up to 15 duplicate calls, an estimated one to two minutes, so its card is the code-built one first. On a Mac that reports the Core model it is unmeasured. Both numbers go into the release gate below.

How many calls a capture costs, and how long. A short note is one extraction call, one binder call per item, and one duplicate call per item that has candidates. A five-minute dictation of about 750 words is five windows, up to 20 binder calls and up to 20 duplicate calls. On the M5, one extraction window took 7.75 s in English and 6.14 s in French for the whole `fm` process, a binder call 0.78 s and a duplicate call 0.7 to 1.07 s. So a five-minute dictation with 20 items takes about 65 to 70 seconds even on the M5 with the larger model, and for such a capture the minute is met by the code-built card of 3.4, with the clerk's reading following. These timings are for the M5 and the Core Advanced model only. On a Mac that reports the 3B Core model, latency and recall are unmeasured (capture-event-v0 §10.5), and under the Background classification of 3.1 they may be slower still.

What the samples got wrong. In the planning session's runs, extraction dropped an item's amount ("two thousand"), listed "Estate of A" as a person, invented an item from "no wait, that is next year", and copied a time expression into an item whose own quote had none. The first design-skeptic pass found that the most common failure is a time word left out: in the 639-word run, items came back with no time words for "by Friday", "next week", "end of the week", "by Wednesday" and "by the end of the month". In the 148-word window, "the second Tuesday" became "next meeting". In an invented French window, "quatre mille deux cents dollars" came back as "deux mille deux cents dollars", "d'ici vendredi" was lost, and "moi-même" was given as a time. The second pass added the six-item drops above, the binder chosen without context, and a duplicate call that matched a new payment task to an old repair item (section 8, step 4).

The code checks are those of capture-event-v0 §6.4, with the same results: an item whose quote is not in the capture is dropped and counted, a time expression or amount not in the item's own sentence is dropped, and sentences that no item covers are listed as unfiled. Two checks are added here and asked of the spec (section 13), because the spec's checks only remove wrong values and do not catch missing ones:

- Time words. Code runs the date grammar of capture-event-v0 §6.6 over each anchored sentence. When it finds a time expression that the item's `when_text` lacks, it fills `when_text` from the sentence and flags the card "date taken from the sentence".
- Numbers. When the sentence holds an amount (in digits or in words, English or French) that the item lacks or that differs from the item's amount, code flags the card "amount in the note not found in the item" and shows the sentence's amount.

The release gate. Before the clerk ships, and after every model update, an invented English and French fixture set with expected items, dates, amounts and binders is run through the Swift clerk itself, never through `fm`, on a Mac that reports the 3B Core model and 4,096 tokens. It measures recall, tokens and latency per call, against a pass bar for each call, with the runtime classified Background (3.1). Apple's Evaluations framework is new in macOS 27 and may host it (web-apple-fm). Custom adapters are obsoleted in macOS 27 (web-apple-fm), so fine-tuning is not a lever; the levers are the instructions, the window size, splitting tasks further and code checks, and the recommended fallback model is smaller still (5.6). If the Core model fails the bar, the clerk ships on such Macs in a reduced form, in this order of preference: smaller windows; or its reading shown as suggestions beside the Tier 0 card; or off, with Tier 0 cards only. The release notes say which. The doctor's "prompts not yet re-tested on this model version" refers to this set.

### 5.4 What Tier 1 never does, and how model errors are handled

- It never reads a binder. It sees one window of one capture, and at most the retrieved facts the table allows.
- It never emits ops. It emits an interpretation; code builds the proposal (decisions.md C3).
- It never resolves a date, computes an amount or decides a statutory deadline (decisions.md P9).
- It never reconciles a binder, cross-references documents or drafts letters. Those are Tier 2 (decisions.md P5).
- It never sees the name of a binder whose disclosure is `none`. Such a binder is left out of the binder call unless the person added it to the filing list on purpose. An opted-in one is offered under an opaque label such as `binder-3`, with a neutral one-line description the person wrote, and code maps the label back (capture-event-v0 §6.4 step 2). A label with no description carries no meaning the model could match to a sentence, so without the person's description the model would almost never pick it, or would pick it at random. Items for a binder left out normally land in "not sure", and the person picks the binder on the card, where the real name shows only inside the app.
- It never receives untrusted text in its instructions. Captures, document text, binder names and candidate items go in the prompt, each under a plain label such as "Note:" or "Existing items:" (web-apple-fm: instructions must contain only trusted content).
- It never calls tools. Retrieval is done by code before the call, which keeps the token count predictable.
- It never runs on text in a language the model does not support. `supportsLocale` is checked first (web-apple-fm: 24 locales, Ukrainian not among them; decisions.md P8).
- It never runs two calls at once: one session per call, one call in flight (web-apple-fm). It streams only so that code can keep the finished items of a cut-off answer and stop a runaway field (5.3). The old reason not to stream, a 2025 remark that streaming in the background on battery hits the rate limit sooner, concerned iOS; a WWDC26 lab said rate limiting "does not apply at all" on macOS (web-apple-fm). The spike of 5.3 settles it.
- It never applies or sends anything. Private Cloud Compute is not a tier (decisions.md P1).

Model conditions, from the `LanguageModelError` vocabulary (web-apple-fm), and what the runtime does with each:

- `contextSizeExceeded` (carries `contextSize` and `tokenCount`): halve the window and retry once; then that window becomes an unfiled span (5.3).
- `guardrailViolation` and `refusal`: a long but harmless prompt tripped the guardrail in the verifier's probe (web-apple-fm), and a benign 97-word tax paragraph was refused under guided generation with and without permissive guardrails (capture-event-v0 §10.5). Apple's documentation for `permissiveContentTransformations` says that for responses other than `String` it "behaves the same way as default mode" (fetched by the design-skeptic pass on 2026-10-06), and every clerk call uses guided generation, so a permissive retry would change nothing. The retry follows capture-event-v0 §6.4: merge the window with a neighbour, then try once with reworded instructions. After that the refused window goes on the card word for word as an unfiled span with the outcome `partial`, and the other windows' items stand.
- `rateLimited` (optional `resetDate`): wait until the reset date, else 5 minutes (proposed), keep the digest breaker closed, and show "model: rate limited until 14:05". A WWDC26 group lab said rate limiting "does not apply at all" on macOS; that is verbal and untested under load (web-apple-fm), so the code handles it anyway.
- `unsupportedLanguageOrLocale`: Tier 0 with that outcome.
- Availability `unavailable` with reason `deviceNotEligible`, `appleIntelligenceNotEnabled` or `modelNotReady`: Tier 1 pauses, captures take the Tier 0 path, and the Health page shows the reason in the person's words ("Apple Intelligence is off in System Settings"). Tier 0 keeps working.

Every derived event records its producer: tier, model, variant, OS build, `context_size` and prompt version (decisions.md C3; capture-event-v0 §6.2). When macOS updates the model, the doctor flags prompts not yet re-tested on the new version.

### 5.5 The retrieval index

One SQLite FTS5 index per binder at `.sprava/index.sqlite`, over item titles, tags, waiting-on names, document titles and the first page of document text. The system SQLite on macOS 27.0 is 3.54.0 with FTS5 compiled in, so nothing is bundled (web-localfirst-platform). It uses an external-content FTS5 table, whose `rebuild` command recovers from drift; WAL mode (write-ahead logging) with `synchronous=NORMAL` is enough because the index can be rebuilt (web-localfirst-platform: SQLite documentation). The tokenizer is `unicode61`, which handles accented French.

The index is per binder on purpose. There is no cross-binder index, so a compartment stays a compartment, and deleting a binder deletes its index. The extraction call needs no search and gets no binder list. The binder call gets the closed list of binder names with their descriptions, and opted-in binders at `none` under opaque labels (5.4). Retrieval for the duplicate call is a BM25 query (a standard text-search ranking) of the item's sentence over the chosen binder's open items, redacted items included, top 5 to 8 (capture-event-v0 §6.4 step 3). Redaction controls what the hub and cross-binder views show. This call runs on the Mac and holds one binder's content, so leaving redacted items out would protect nothing, and it would make every item filed from a meeting, document or email (private, therefore redacted, by default) invisible to the next capture about the same matter. Embeddings come later through `NLContextualEmbedding` (512 dimensions, 256 tokens, Latin-script assets present on the probe Mac, Cyrillic assets not downloaded; web-localfirst-platform). CoreSpotlight is never used for binder content, because donated items appear in the system Spotlight window (web-localfirst-platform: WWDC24 session 10131; decisions.md A3).

### 5.6 The fallback model seam

The clerk is written against `LanguageModelSession(model:)`. Apple's `SystemLanguageModel` is one implementation of the public `LanguageModel` protocol on macOS 27; `CoreAILanguageModel` (Apple, BSD-3-Clause, `.aimodel` files, about 0.6B parameters recommended) and `MLXLanguageModel` (MLX, requires the 27.0 SDK) are two others, and guided generation works unchanged through them (web-apple-fm; decisions.md P3). The seam costs nothing now, with one guard. The same protocol has conformers that run off the Mac: Anthropic's `ClaudeForFoundationModels`, Google's `GeminiLanguageModel`, and the `ChatCompletionsLanguageModel` of foundation-models-utilities, which accepts any server URL (web-apple-fm). Plugging any of them into the seam would send capture text off the Mac. So the clerk accepts only on-device conformers, checked in code by an allowlist of types, and section 10 lists a cloud conformer as a channel that is not offered. Shipping a fallback model is deferred, and its guided-generation fidelity is unverified (web-apple-fm, gaps), so a fallback is never switched on silently: it must pass the same fixtures as the system model first (5.3). The recommended local fallback has about 0.6B parameters, and nothing shows yet that it can do this extraction, in Ukrainian or otherwise; its quality is unknown until it passes those fixtures. If Ukrainian matters for v1, the fallback moves into the MVP (decisions.md P8, open). The Health page shows which model is active.

### 5.7 Tier 2 over MCP

A brain does the work the clerk cannot: reconcile a long binder, cross-reference documents, draft a careful letter (decisions.md P5). It reads through paginated tools and proposes through one tool that returns a handle at once. It never applies and never approves (decisions.md A4). Section 7 has the surface. Tier 2 is the one path by which binder content can leave the Mac in readable form, which is why it is opt-in per client and per binder and listed in section 10.

## 6. The review queue

The review queue is the main interaction, ahead of any chat, and the only place where anything proposed becomes real (decisions.md A5). It defends boundaries 4 and 5 by putting a person between every model and every catalog.

### 6.1 What a card shows

A card is one proposal. Top to bottom:

1. The source, first, so the person reads the evidence before the claim: the capture's text with the quoted span highlighted and a play button for the audio, or a document's first lines. For a brain's proposal, the source is what Sprava itself looks up from the source references in `propose_ops`: the items and document spans the brain cites, each checked to exist and to lie within that client's scope, shown as excerpts. A reference that does not resolve is flagged "cited but not found". The brain's rationale comes after them, labelled "the brain's explanation", because it is text the model wrote and injected content can steer it (web-mcp-agents: local server security guide). Every string on the card passed through the guard's one sanitizer (4.2 step 6), and a visible mark says when characters were removed, so the text a card shows is the text that will be stored.
2. The change in plain words, one line per op: "Add to Estate of A. Example: Send the original will to the notary, due Thursday 2026-10-08"; "Possible duplicate of estate-example-2026-014: approve as an update or as a new item"; "Related to estate-example-2026-014, added as a new item".
3. The binder guess, as a picker with the guess selected, and the checks behind it (quote found, date resolved, index match) rather than a bare number; "not sure" opens the picker empty. Choosing a binder moves the proposal into that binder and runs the duplicate check there before the card returns. A brain's proposal can be moved into a binder outside that client's scope; what the brain then learns about it is in 6.3.
4. Who proposed it: "Clerk (on this Mac)", "Filed by code, no model", or "Claude Code, client claude-code-1", with the model and prompt version behind a "why" link that opens the derived event. For a capture, also the producer, its device and its folder, and "unverified source" when the event came from a folder with no registered producer (section 8).
5. Flags when they apply: "needs a look" when an `expect` fingerprint no longer matches (4.6), with a short diff; "the clerk's answer was cut off"; "amount in the note not found in the item"; "date taken from the sentence"; "part of this note is not filed yet" with the unfiled spans in the capture's own words; "filed by code to stay within a minute; the clerk's reading will follow"; "hidden characters removed".
6. Buttons: Approve, Edit, Reject. Edit opens the ops as a form; the edited batch is applied with actor `user` and the proposal id kept, so the log records that a person changed the clerk's reading. Reject asks for an optional reason, kept on the proposal.

### 6.2 Rules

- Tier 1 and Tier 2 proposals look the same. Only the "who proposed it" line differs (decisions.md A5).
- No automatic approval in v0. "Monitors flag, humans act" (HANDOFF).
- Approval is per proposal. "Approve all from this capture" is offered as one combined action only when every op is additive (`add_item`, `file_document`), every concrete check passed (every quote anchored, every date resolved, no number or time-word flag, no "may have missed items" flag), and the capture came from a registered producer, or, for the app's own folder, matches a notice the app sent over XPC (section 8). It is never offered for `update_item`, `set_status`, `complete`, `drop` or `set_disclosure`, and never on a scalar confidence, which a capture's own text or a brain could push up. There is no "approve all" across captures. A confidence threshold is considered only after it has been measured against the labelled fixtures of 5.3.
- After approval the card stays visible for 7 days with Undo (a compensating op, 4.4), and the item's history keeps Undo forever.
- A follow-up proposal from the nudge job ("follow up with the property manager; they said by 10 October, 4 days ago") offers the clerk's one-line draft as text to copy, once the draft has arrived. There is at most one pending follow-up per item; the job refreshes it in place (3.4). Sprava sends nothing.
- The queue is files in `.sprava/proposals/` and `unfiled/`, so a terminal agent can read it and the runtime never needs the app to be open. The runtime trusts only the proposals it wrote itself (4.6).
- While the runtime is down the queue is read-only, with the banner of section 2.1. There is no second writer.

### 6.3 Housekeeping

- A proposal untouched for 30 days moves to a "Later" tab and stays `proposed`. Nothing is deleted (4.6).
- A proposal pending for more than 7 days is a note on the Health page, because the person is also a component that can go silent.
- A macOS notification says only a count, such as "3 proposals waiting", never a title, because notifications can appear on a locked screen (3.7). The daily summary of 3.4 carries the same kind of counts for deadlines, so a due date is not missed while the app stays closed.
- A brain learns a proposal's outcome by calling `get_proposal`. The outcome is projected by the binder the proposal now lives in, which may differ from the one the brain named (6.1). It sees a rejection reason only if the person typed one and that binder's disclosure is `full`. If that binder is outside the client's scope, or at `none`, `get_proposal` and `list_proposals` return a neutral "closed" state with no op ids and no reason, so a brain never learns that such a binder exists (boundary 5).

Where elicitation exists (MCP's way for a server to ask the person a question through the client's own interface; 7.4), a brain's conversation can show "a proposal is waiting in Sprava, open it?". That is a convenience, never the approval.

## 7. The MCP surface

This section defends boundary 5 and much of boundary 3. The MCP specification itself says tool annotations are untrusted unless they come from a trusted server and that a person should be able to deny a tool call (web-mcp-agents). Sprava also takes the server's side of that seriously: it never trusts the client.

### 7.1 Transport and eras

The listener uses a Unix domain socket at `~/Library/Application Support/Sprava/mcp/mcp.sock`. Each brain launches a shim, `Contents/MacOS/sprava-mcp`, which speaks stdio to the client (newline-delimited JSON-RPC, the message format MCP uses, one JSON message per line) and forwards to the socket. The MCP specification says the stdio wire format works unchanged over Unix domain sockets and that custom transports over such streams should reuse it, and its security guidance names Unix sockets with restricted access as the way to restrict a local server (web-mcp-agents: specification 2026-07-28, stdio transport and security best practices; decisions.md A4). There is no HTTP listener.

Eras: the current revision is 2026-07-28. It is stateless: there is no `initialize` handshake, every request carries its protocol version and the client's capabilities in `_meta`, servers must implement `server/discover`, and server-to-client requests travel as "input required" round trips. The previous revision is 2025-11-25, with the `initialize` handshake. A modern client with a legacy server fails and a legacy client with a modern server fails; only a dual-era server works with both (web-mcp-agents: versioning page). Clients today sit on both sides (7.8). The listener is dual-era (decisions.md A4): it picks the era from the first message on each connection (`server/discover` or a request carrying `_meta` is modern; `initialize` is legacy) and serves both at once, which the specification allows.

Implementation: a hand-rolled dual-era JSON-RPC server in Swift (decisions.md A10, open). The official Swift SDK is Tier 3 (no delivery commitment) at 0.12.1 and covers 2025-11-25 only; the Python SDK v2 is dual-era, but bundling a Python runtime is the price (web-mcp-agents). An option for sequencing that leaves A4 unchanged: build the modern era first, because Claude Code (how the author drives binders today) negotiates it on stdio, and add the legacy era second, before any release that names Claude Desktop or Gemini CLI as supported. The dual-era target stays as decided.

If the runtime restarts, every shim's socket closes; the specification tells clients to restart a stdio server that exits, and in-flight requests are lost because the protocol is stateless (web-mcp-agents). The shim keeps no state; the listener never relies on an earlier request on the same connection, and keeps per-connection state only for the era and the client's identity.

### 7.2 The shim and the socket

The socket is mode 0600 inside a 0700 folder. A Unix socket address holds at most 104 bytes on macOS, the terminating byte included (`man 4 unix`: `sun_path[104]`; platform knowledge, not from the research), so a longer path cannot be bound or reached; the runtime checks the length at start and the doctor reports it. A crash leaves the socket file behind, and binding to it again fails until it is removed, so the runtime removes a stale socket file while it holds the lease (3.2) and then binds.

`sprava-mcp` is a small signed binary in the bundle. A brain starts it as a stdio server with one argument, its client id (`--client claude-code-1`), and with the client's token in its environment (`SPRAVA_CLIENT_TOKEN`), set by the client's own server settings (7.5). It does four things and nothing else:

1. It connects to the socket and authenticates within a short timeout (proposed: 3 seconds). If that fails, it answers the client's first request with a JSON-RPC error that names the part that failed, and exits with a non-zero status, so the client shows the reason and starts the shim again later (web-mcp-agents: stdio transport rules). The messages are distinct, so the wrong part is never blamed (HANDOFF "A slow hook was misdiagnosed"):
   - no socket file: "the Sprava runtime is not running";
   - the connection is refused or nothing answers in time: "the Sprava runtime is not answering (last heartbeat N s ago)", with the age read from `heartbeat.json`;
   - the listener paused this client: "Sprava paused this client until 14:05 (budget)";
   - the token is missing: "no Sprava token in this client's settings; see Sprava > Brains";
   - the token is refused: "Sprava client token expired or revoked; renew it in Sprava > Brains".
2. It sends one preamble line that is not JSON-RPC: `{"sprava_auth": {"client_id": "claude-code-1", "token": "…", "shim_version": "0.1.0"}}`. The listener answers with one line, `{"sprava_auth": {"ok": true}}` or an error code, and from then on the connection speaks MCP. The listener accepts shim versions within a stated range (proposed: the same major version, and a minor version no newer than its own). After an update that the person has not followed by opening the app, the old runtime may meet a newer shim; it then answers with the code `runtime_older`, and the shim tells the client "Sprava was updated; open Sprava once to finish". The runtime also restarts itself at a quiet moment when it sees its own executable replaced (2.1).
3. It copies newline-delimited JSON-RPC lines between stdio and the socket unchanged. It never parses MCP content, so nothing in a tool call or a result can exploit it. A line longer than 4 MiB closes the connection; that limit leaves room for a 1 MiB document body after encoding (7.3).
4. It exits on end of input and on SIGTERM, and writes only MCP to stdout and its own messages to stderr, as the stdio transport requires (web-mcp-agents).

On its side, the listener rejects any peer whose user id differs from its own (read from the socket with `getpeereid`), and accepts the preamble only when the token matches a registered, unrevoked client whose sealed record is intact (7.5). Any program running as the person can connect to the socket without the shim, so limits the shim enforces protect nothing; the listener enforces its own. Before authentication it allows one preamble line of at most 4 KiB, a preamble timeout of 3 seconds, and at most 8 unauthenticated connections at a time (proposed). After authentication it closes a connection on any line longer than 4 MiB. Everything runs in one process, so an oversized line or a pile of idle connections must not be able to take down the heartbeat, the guard and the clerk together. It may also read the peer's code signature from its audit token, but only as a diagnostic ("the peer is our shim"), never as a defence: an attacker running as the person would simply launch the genuine shim. Whether that check works is a spike (13).

What the token is worth. The specification says a client and its stdio server share one trust domain and that stdio is not a sandbox (web-mcp-agents: local server security guide). So the shim is treated as part of the brain. A per-client token gives attribution, scope against an honest client that makes mistakes, budgets and revocation. It does not authenticate a client against other code running as the same user, which can read the client's settings. Every check lives in the runtime, and the listener trusts nothing the shim says except a valid token.

### 7.3 Tools

Tool names are short so they survive clients that prefix and cap them: Gemini CLI rewrites names as `mcp_<server>_<tool>`, capped at 64 characters (web-mcp-agents). Descriptions stay under 2,048 characters, where Claude Code truncates them (web-mcp-agents). The tool list is the same for every client and never varies per connection (web-mcp-agents: `tools/list` must not vary per connection; decisions.md A4); it is served with `ttlMs` and `cacheScope`. What varies is what a call may return, decided by the client's scope and each binder's disclosure (7.6). Every tool sets all four annotations explicitly, because the specification's defaults are `readOnlyHint` false, `destructiveHint` true, `idempotentHint` false and `openWorldHint` true (web-mcp-agents: schema). Below, "read-only" means `readOnlyHint` true, `destructiveHint` false, `idempotentHint` true, `openWorldHint` false.

| Name | Purpose | Annotations | Scope needed | Pagination |
|---|---|---|---|---|
| `list_binders` | Binders this client may see, with disclosure level and counts | read-only | read | cursor, 50 per page |
| `get_now` | One binder's Now page: the eight buckets of decisions.md F4 | read-only | read on the binder | by bucket, 50 items per page |
| `list_items` | Items filtered by status, bucket, tag, waiting-on, changed since | read-only | read | cursor, 50 per page |
| `get_item` | One item, with its history and sources at `full`, all through the projection (below) | read-only | read | history 50 ops per page |
| `list_documents` | One binder's documents: id, title, date, kind, size, as disclosure allows | read-only | read | cursor, 50 per page |
| `search` | Full-text search inside one binder, as disclosure allows; redacted items and private documents never match | read-only | read | cursor, 20 per page |
| `read_document` | The extracted text of one document | read-only | read, disclosure `full`, and the client's `document_text` flag | by page, at most the client's `max_result_chars` per page |
| `list_proposals` | This client's own proposals and their status | read-only | read | cursor, 50 per page |
| `get_proposal` | One of this client's proposals, with its state and, once applied, the applied op ids | read-only | read | n/a |
| `propose_ops` | Submit an op batch for one binder, with a rationale, source references and a client request id; new items use placeholders, never ids; validated at once; returns `{proposal_id, state: "proposed"}` immediately and never waits for the person | `readOnlyHint` false, `destructiveHint` false, `idempotentHint` true (by request id), `openWorldHint` false | propose on the binder | n/a |
| `withdraw_proposal` | Withdraw one of this client's pending proposals | `readOnlyHint` false, `destructiveHint` false, `idempotentHint` true, `openWorldHint` false | propose | n/a |

There is no approve, apply, delete or settings tool. MCP has no first-class object for "a change awaiting approval"; approval is the host's job, so the sound model is a propose tool that returns a handle and the real approval in the app (web-mcp-agents; decisions.md A4). A call that waited for the person would also hit client timeouts. Clients differ in when they ask the person, and the design must not assume one behaviour (critique.md). Anthropic's connector criteria let read-only tools of hosted Claude connectors run without per-call confirmation and always prompt for destructive ones. For local servers, Claude Desktop asks on every tool call, Cursor and VS Code confirm by default, and Claude Code follows its permission rules (web-mcp-agents). Where reads do run unprompted, an injected brain can read its whole scope without the person seeing it. So Sprava offers, per client, Claude Code's `anthropic/requiresUserInteraction` on `read_document`, which makes Claude Code ask before every document read; it is documented for Claude Code only (web-mcp-agents), and the registration screen suggests it for binders that hold other people's documents.

`propose_ops` validates the batch against the teka-v0 schemas before storing it. A batch that fails returns a result with `isError: true` and the reasons, so the model can correct itself (web-mcp-agents: tool execution errors go in the result). A handle is a name, never a capability: every later call re-checks that the handle belongs to the calling client (web-mcp-agents: stateful tools guidance). Ids that a client supplies for `add_item` are rejected; new items use placeholders, and the guard mints ids at approval (4.2).

A brain may propose a new document only as a `file_document` op that carries the content. The brain never chooses where it lands, and nothing reaches the binder's visible folders before the person approves. Until then the body is held inside the proposal, in `.sprava/proposals/<id>/`, and covered by the proposal's digest (4.6). It never goes into `intake/`: that is the terminal agent's drop zone, and the manual stamped into every lifeproj binder tells agents to drain `intake/`, file what they find and record it in `catalog.json` (lifeproj-schema: the digest ritual, `templates.py`). A pending, possibly injected, document there would be filed by the next terminal digest without the person's approval, against decisions.md A4 and A5. On approval the guard creates the file, with `O_EXCL` and `O_NOFOLLOW` so it never overwrites or follows a link, directly in a document folder (proposed: `correspondence/`, or the binder's documents folder of teka-v0 §9.7) under a name the runtime chooses, `<date>_<uuid>.<ext>`, and records that path. The runtime accepts only extensions on an allowlist and refuses any name that starts with a dot or matches a known agent file (`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.agents/`, `scripts/`). Otherwise an approved proposal could plant hooks or a manual that a later terminal agent would run, which defeats decisions.md F9. The card shows the path the file will get. The body is at most 1 MiB once decoded, sent as base64 for a binary file; the listener's line limit of 4 MiB leaves room for that encoding (7.2). This write is listed with the others beyond decisions.md F1 (section 13, item 36). The same rule applies to the app's own dropped documents: capture-event-v0 §6.5 copies a dropped document into `intake/` before the proposal, and section 13 asks it to hold the file in the app's capture store until approval instead.

`read_document` follows containment rules: the document's `path` must resolve inside the binder folder, its extension must be on an allowlist, no symbolic link is followed at any step, and every refusal returns the same "not found" as a document that does not exist. File paths are never exposed (web-mcp-agents: servers must sanitize paths).

Every read goes through the projection, history and search included:

- History. `get_item` returns only the ops that touch that item, with their args projected under the binder's disclosure and the item's `redact` and `slice_title`. An `external_edit` patch is cut down to the paths of that item. Provenance that names another binder is removed.
- Search. Redacted items and private documents are left out of matching as well as out of snippets, because a list of hits answers yes or no about them.
- Private documents. A filed private capture, and any document filed from one, carries a document-level marker (`documents[].sensitivity: private`, a teka-v0 addition requested in section 13). `read_document`, `list_documents`, the index and `get_item` sources all honour it, so the text of a private capture is never returned over MCP. Removing or lowering the marker widens what leaves the binder, so only the person may do it, through a privacy card in the app. `propose_ops` rejects an `update_document` that removes or lowers it, and an outside edit that does so waits for a card (the privacy ratchet, 4.5).

Results are returned as `structuredContent` matching the tool's `outputSchema`, plus the same JSON as a text block for older clients (web-mcp-agents). Because the same content is sent twice, the size limit of 7.7 counts both copies.

### 7.4 Resources, prompts and confirmation

Resources, through resource templates: `teka://<binder>/now` (the Now page as Markdown), `teka://<binder>/items/<id>` and `teka://<binder>/documents/<id>`. `resources/read` goes through the same projection call as the matching tool, with every check that tool applies: scope, disclosure, containment, the `document_text` flag, the private marker, `max_result_chars`, the client's budgets and the audit log. Resource templates support argument completion (web-mcp-agents); completion goes through the same call and offers only binders in the client's scope, so it can never list a binder's name the client may not see. Anything not found or not allowed returns the same error. Prompts are user-controlled and appear as slash commands in Claude Code and Gemini CLI (web-mcp-agents): `reconcile`, `draft-follow-up` and `cross-reference`. Each prompt states the rules: read with the tools, propose with `propose_ops`, never claim to have changed anything. Resource and prompt lists never vary per connection either.

Confirmation in the conversation: where a client renders elicitation (Claude Code on direct stdio connections, Codex, Cursor and VS Code; hosted Claude and Gemini CLI do not; web-mcp-agents), `propose_ops` may return an "input required" round trip asking "A proposal with 4 changes is now in your Sprava review queue. Open it?" with a yes or no. Form-mode elicitation carries only flat primitive fields, so the diff is summarized in the message (web-mcp-agents). The answer never approves anything (decisions.md A4). The proposal is stored before the question is asked, so a client that never retries still gets its `proposal_id`, through idempotency on its request id; the specification says servers must not assume the client will retry. Any `requestState` the listener returns is HMAC-signed (a keyed hash only the runtime can produce), bound to the client, short-lived, carries a digest of the originating request, and is accepted only once, which the runtime enforces (web-mcp-agents: MRTR). The question is asked only on modern-era connections, and only for a client whose sealed record has the elicitation flag on. A declared capability is not enough: Cowork's embedded client runs on 2026-07-28 and declares `elicitation`, but renders nothing and hangs until a 180-second transport timeout (web-mcp-agents, issue #1046), and `clientInfo` is only what the client says about itself, so it proves nothing. The flag is off by default and is turned on per client type once that type has been tested. Legacy-era clients would need a server-initiated `elicitation/create`, and the eras of Codex, Cursor and VS Code are not stated (7.8), so they get the same information in the tool result text, as do clients without the flag.

### 7.5 Per-client registration and tokens

The app has a "Connect a brain" screen. The person picks the client (Claude Code, Claude Desktop, Codex, Cursor, VS Code, Gemini CLI, other), the binders, a level per binder (read, or read and propose), and the client-wide settings: whether document text may be read (`document_text`, off by default), the largest result (`max_result_chars`), and its budgets. The screen says three things plainly. First, the moment a binder is in a client's scope, its content within disclosure goes to the model provider that client is configured to use, which Sprava cannot know (section 10). Second, a client with its own file or shell tools can read binder folders directly, and Sprava's scope applies only to what the client asks Sprava. Where the client offers its own controls, the screen suggests them, for example Claude Code permission rules that deny Read, Edit and Write on binder folders, on the capture root and on `~/Library/Application Support/Sprava`, or a client sandbox mode; Sprava cannot verify them. A brain that can write into the capture root can forge a capture event (section 8). Third, `document_text` is off because filed documents hold other people's words, and a letter can carry instructions to the brain (7.7).

The app then:

1. Writes a client record to `mcp/clients.json`: id, display name, type, binders and levels, flags (including whether elicitation may be used, 7.4), budgets, created date, an optional expiry, and a SHA-256 of the token. The record holds no secret. Each record is sealed with a keyed hash under the runtime key, the same key that seals op-log lines (4.1). The runtime accepts a change to a client's scope, flags or budgets only over XPC from the app. A record whose seal does not match was edited elsewhere: the client is paused, its scope is treated as the last sealed one, and the doctor reports tampering. A change that widens a scope also goes through the privacy ratchet (4.5).
2. Generates a random 32-byte token with the fixed prefix `sprava_ct_`, so the doctor and common secret scanners can recognize it, and shows it once, inside the exact registration snippet. When the person copies it, the app marks the pasteboard item as current-host-only, so Universal Clipboard does not carry it to the person's other devices, and as concealed and transient, so well-behaved clipboard-history tools skip it, and clears it after 60 seconds (proposed). These pasteboard markers are platform knowledge, not from the research. The token lives with the client, in the environment entry of that client's own server settings, as decisions.md A4 says ("registered with a per-client token in its environment"). For Claude Desktop the app offers a `.mcpb` bundle (Claude Desktop's one-click install package) whose token field is marked sensitive; Claude Desktop stores it in the OS keychain and injects it into the shim's environment at launch (web-mcp-agents: manifest 0.3). That is the best path where a client offers it.
3. Shows the exact registration, with every argument and nothing truncated, as the one-click install rule (SEP-1024) requires of clients (web-mcp-agents). The shape is the same for every stdio client: a command, `/Applications/Sprava.app/Contents/MacOS/sprava-mcp`, the arguments `--client claude-code-1`, and the environment entry `SPRAVA_CLIENT_TOKEN`. These CLIs take the token as an argument (`--env K=V` or `-e K=V`; web-mcp-agents), and a command the person pastes into a terminal writes the raw token into the shell history file, which is plain text and backed up, and briefly shows it in the process list. So for `claude mcp add`, `codex mcp add` and `gemini mcp add` the app shows the exact command and then, with the person's go-ahead, runs the CLI itself, passing the arguments directly with no shell. For Claude Code it always uses `--scope user`: a `--scope project` entry would write `.mcp.json` into the current folder, which may be a git repository or a binder, and Sprava never generates one. Where running the CLI is not possible, the app gives a config-file snippet instead of a shell command. Cursor's and VS Code's `mcp.json` and Claude Desktop's config or `.mcpb` bundle get snippets or the bundle. Registering a client asks for Touch ID or the login password (2.1).

Why the token is not in Sprava's Keychain. The first draft kept the token in the Keychain and let the shim fetch it by the client id in its arguments. Client ids are not secret: they are in `clients.json`, in the registration command and in client configs. Any program running as the person could then run the genuine shim with any client id and get that client's scope, since the shim would fetch the token for whoever launched it. (Whether Keychain access is decided per access group or per calling program is not in the research; the digest says only that the data-protection keychain is required when an access group applies. Spike (g) of section 13, item 39, covers it.) A token in the client's settings at least means that launching the shim needs the secret. The cost is the lesson about secrets in config files (HANDOFF): the token sits in a client config file that other programs can read and backups copy. The doctor therefore reports which clients keep it in a plain file, prefers the `.mcpb` path where it exists, and warns when it finds a Sprava token anywhere else, such as a shell profile or a shell history file. A Keychain item that asks for Touch ID or the password once per session per client, naming the client, is the stronger alternative, kept open in section 13.

Lifetimes and limits (all proposed):

- Tokens have no forced expiry by default. A forced expiry would rebuild the 7-day OAuth lesson, where a credential expired and a working integration stopped (HANDOFF), and it protects little here: row 4 of the threat model already accepts that code running as the person can read the client's settings. The person may set an expiry per client. Then a notification comes 14 days ahead, every tool result carries a warning line once fewer than 14 days remain, so the brain tells the person, and the shim's message after expiry says what to do (7.2).
- A client with no call in 90 days is suggested for revocation.
- Revocation is one click and immediate: the hash is removed, open connections for that client are closed, and its pending proposals are withdrawn. Renewal issues a new token and shows the snippet again.
- Each client has budgets: 60 calls per minute, 2,000 calls per day, and 50 MB of results per day. They run through the same breaker wrapper as every job (3.5); a call over budget returns an `isError` result with the reset time, and repeated failures pause only that client (3.4). Calls today against each limit are on the Health page.
- Each client's calls are recorded in `mcp/audit/<client>.ndjson`: time, tool, the binder's opaque id, result size in bytes, duration and outcome. Never content, never titles, never folder names (3.7).

### 7.6 Disclosure enforcement

Two settings meet at every call: the client's scope (which binders, at which level) and the binder's `disclosure` (decisions.md F6). The scope decides whether a binder is reachable at all; disclosure sets the ceiling on what any reachable call returns. Lowering a binder's disclosure lowers it for every client at once. The projection is the one in teka-v0 §5.5, and per-item `redact` and `slice_title` apply on top at every level, exactly as at the hub's slice boundary: an item can be more hidden than its binder, never less.

| Disclosure | `list_binders` | Items (`get_now`, `list_items`, `get_item`) | Documents (`list_documents`) | `search` | `read_document`, history and sources |
|---|---|---|---|---|---|
| `full` | Name, description, counts | Every field the binder owns; `slice_title` replaces the title, and `redact: true` gives "[redacted]", masks `waiting_on` as "[party]" and sets `link` to null | Title, date, kind, size | Items and documents, with snippets | Yes, when the client's `document_text` flag is on |
| `title` | Name, description, counts | id, title (with the same per-item rules), status, priority, due, `no_deadline`, tags (empty for a redacted item), `kind`, `follow_up_at`; `waiting_on` as "[party]" for every item; `link` null | Titles only | Item titles only, no snippets | No |
| `kind` | Name and counts | id, status, priority, due, `no_deadline`, `kind` (`other` when missing), `follow_up_at`; title "[redacted]" and `waiting_on` "[party]" for every item; tags empty | Kind and date only | No | No |
| `none` | Absent | n/a | n/a | n/a | n/a |

A call that names a binder outside the client's scope, or a binder whose disclosure is `none`, returns the same "not found" result as a binder that does not exist. A client therefore cannot list compartments by probing names. This matches the hub, where an absent binder is invisible by design, never an error.

The listener has no code path that reads a catalog except through the slice projection module (2.1), the same module that writes hub slices and feeds the Today page and the roll-up. Inside one process there is no federation to rely on, so this one code path is the federation.

Captures marked `sensitivity: private` (decisions.md C1) never reach the Today page or any MCP answer while they wait in the queue. When one is filed, its proposal sets `redact: true` and a `kind` on the items it creates, so every cross-binder surface shows only the kind (capture-event-v0 §3.3), and the capture's own text is never returned over MCP: the filed copy and any document filed from it carry the private marker that every read path honours (7.3). The person sees these settings on the card and can change them.

The clerk is not subject to disclosure: it runs inside the runtime, on this Mac, and its binder list follows 5.4. The Today page applies the same projection (decisions.md A8). The disclosure, `redact` and `slice_title` values every surface projects with are the last ones the person confirmed in the app; a widening change made outside the app waits for a privacy card (4.5).

### 7.7 Security

- Tool poisoning and rug pulls. The attack hides instructions in tool descriptions, changes descriptions after approval, or lets one server's descriptions hijack another's tools; a 2026 paper showed Unicode TAG-block characters that are invisible in approval dialogs but reach the model (web-mcp-agents: Invariant Labs 2025-04-01; arXiv 2607.05744). Sprava's descriptions are static, describe only what the tool does, mention no other tool or server, never change at runtime, and are versioned in the capability manifest. A build-time check fails the build on any non-ASCII byte in a description. The SHA-256 of the whole tool catalog is published in the manifest and the generated docs, so clients that pin tool lists can verify it. Against poisoning by another server in the same client, Sprava can only limit the damage: its tools can do nothing except read within scope and propose.
- Confused deputy. The token names the client; the listener re-checks scope and ownership on every call and never trusts a handle (web-mcp-agents: state handles are not authentication). The runtime holds no credentials for any other service and never acts toward a third party, so there is nothing to be tricked into using.
- Prompt injection through binder content. Some binder text was written by other people (a letter from the notary, an email from the property manager). Text returned by a tool is data to the brain, and the specification puts no trust marking on content (web-mcp-agents). The listener returns binder text only inside typed result fields, wraps document text in clear begin and end markers, and puts no instructions in results. Stored text already passed the guard's one sanitizer (4.2 step 6); the listener applies the same sanitizer to every result and every proposal it accepts, so text a brain sends and text a brain receives are cleaned by the same code. For changes to binders the guarantee is structural: a brain can only propose, and a person reads the proposal with its source before anything changes. Proposals are not the main injection risk, though. A letter or email filed in a binder can tell a brain to send everything it can read through its other tools: web fetch, shell, or another MCP server in the same client. The trust domain covers all of a client's servers, and injected content can steer an honest server into the same overreach (web-mcp-agents: local server security guide). Sprava cannot stop that inside the client. It keeps `document_text` off by default and says why on the registration screen, and it advises that binders holding other people's documents be shared only with clients that have no web or shell tools enabled, or not shared at all.
- The shim is not a sandbox (7.2). It holds no logic beyond framing and the token.
- A brain's own file tools. Clients with file and shell tools can read binder folders, `shelf.json`, the capture root, the spool and `.sprava/proposals/` directly. Scope, disclosure, budgets and the counters of section 10 cover only what passes through Sprava (boundary 5).
- Timeouts. Reads have a 30-second budget and proposals 5 seconds (proposed), under the clients' own limits: Claude Code moves a call still running after two minutes to the background unless an elicitation dialog is open, and hosted Claude allows 240 seconds per call (web-mcp-agents).
- Output size. Claude Code caps tool results at 25,000 tokens by default (`MAX_MCP_OUTPUT_TOKENS`) and saves larger ones to a file; hosted Claude takes about 150,000 characters (web-mcp-agents). That spill file is a plaintext copy of binder text outside every compartment and every backup rule (section 10). Results default to 20,000 characters (proposed), configurable per client, and for a Claude Code client `max_result_chars` is capped so that both copies of a result (7.3) together stay well under the spill threshold. Every list paginates (decisions.md A4), and a cut result says `truncated: true` with a cursor, never silently.
- No network. The listener never resolves a name or opens a network socket. Nothing in a tool argument is treated as a path outside the binder or a URL to fetch.

## 8. The capture pipeline

> **Reframed by decisions.md P12 (2026-10-07).** Sprava receives text and does not care how it was produced
> (keyboard, built-in dictation, a commercial tool, holos). The app's note field and any adapter that writes
> the capture-event format are producers on equal terms. Documents, images and videos will arrive through an
> adaptation layer whose design is open. Where this section names holos as the producer, read "an adapter".

This section defends boundaries 3 and 4 on the way in. Captures are the one input that arrives without the person typing it into Sprava, so each step treats the file as untrusted data.

holos is the producer (decisions.md P6, P7). It writes one immutable JSON file per finished dictation or saved meeting into a folder the person chooses: `<capture-root>/<device-id>/<id>.json`, with media beside it, written atomically, never modified and never deleted by the producer (decisions.md C2). Sprava never reads holos's private files as its contract, because `dictations.jsonl` has no cursor and is rewritten in place, the retention sweep deletes records and audio after 7 or 30 days (default 30), holos offers no notification, socket or callback, only files, and Apple announced tighter Full Disk Access controls on 2026-10-02 (holos-formats; decisions.md P7). Until holos ships the hook, a developer-only importer reads `voiceislocal history list --json` and `session export --format json` and writes the same event files (decisions.md P7); it is a developer tool, run by hand and not supervised by the runtime.

The app is a producer too. A typed note or a dropped document becomes a capture event in Sprava's own device folder under the capture root (capture-event-v0 §8.1, §8.2), and from there it takes exactly the same path as a dictation.

Producers are registered. The capture folder has no producer authentication of its own: any program running as the person, a synced phone inbox or a terminal brain can write an event that claims to come from holos or from Sprava. capture-event-v0 §3.2's rule that an event never supersedes one from another `source.app` relies on that self-declared field. So at setup each device folder is registered in `capture/producers.json` with the producer the person expects there (Sprava's own folder, holos on this Mac, later a phone). An event whose `source.app` does not match its folder's registered producer is quarantined. An event in a folder with no registered producer is read, but its card says "unverified source" and it is never offered for "Approve all" (6.2).

Registration is bookkeeping, not authentication. It stops one producer from superseding another's events. It does not prove who wrote a file: every device folder is an ordinary 0700 folder that any program running as the person, or a brain with write or shell tools, can write into. For Sprava's own folder the app proves its events. Each time it writes one, it sends the event id and SHA-256 to the runtime over XPC (2.1), and the runtime records them in `capture/app-notices.ndjson`. An event in the app's folder with no matching notice is shown as "unverified source": its `binder_hint` is ignored and "Approve all" is not offered. The holos folder has no such proof in v0; its events are trusted as far as the registration goes and no further, and the card names the producer. The capture root is in the deny rules the registration screen suggests for brains (7.5).

Stages, each idempotent by event id and recorded in `capture/journal.ndjson`, so a crash resumes at the last finished stage. Before a risky stage (a model call, text extraction) the journal records the attempt, and an input that crashed the same stage twice is set aside by the poison rule of 3.4.

1. Watch. File events on the capture root plus a sweep every 15 seconds (proposed) and on wake. File events make detection fast; the sweep guarantees it when an event is dropped or merged, within about 15 seconds (3.4). A capture's landing time is the event file's birth time, or the producer's rename time when it records one (3.4). Producers publish by rename, so a file counts once it exists under its final name; names starting with a dot are a producer's temporary files and are ignored. The watcher never takes locks and never writes into the capture folder. It refuses a capture root or device folder that other users can write or that another user owns. It applies the rule of `read_document` (7.3) that no symbolic link is followed at any step: it refuses a device folder that is a symbolic link, checks each path component with `lstat`, compares the real path with the expected one, and opens each event and media file with `O_NOFOLLOW`, accepting regular files owned by the runtime's own user only. `O_NOFOLLOW` alone checks only the last part of a path, so a linked folder would pass it. Media paths must resolve inside the event's own device folder. Otherwise filing could copy any file the person can read, such as another binder's document, into the target binder, where `read_document` would serve it.
2. Validate. The event is checked against `capture-event.schema.json` and the reader rules of capture-event-v0 §5.3. A malformed file is set aside in `capture/quarantine/` with the error, counted on the Health page by event id only. A file with a newer format version than the runtime knows is listed as "written by a newer producer" and left alone. Events are deduplicated by id. A later event may `supersede` an earlier one only within the same registered producer's chain (capture-event-v0 §3.2). When the earlier event's proposal is still pending, the replacement is shown as a card ("this note was corrected; review the new reading"), never as a silent swap; when it was already filed, code builds a change proposal (capture-event-v0 §6.5). A retraction follows capture-event-v0 §3.2 and is always a card.
3. Interpret. The locale is checked with `supportsLocale`; then the call plan of section 5.3 runs, one session per call, under the capture's one-minute deadline (3.4): one extraction call per window, one binder call per item, and one duplicate call per item that has candidates. Documents are first turned into text by the extraction helper (2.1). A holos meeting is read in the bounded way of 5.3: its action items with the turns they quote, or its first windows marked `partial`; its summary and action items arrive as derived events with `producer: holos` (decisions.md C4), and its transcript is filed as a document. When the model is unavailable, the locale is unsupported, the breaker is open or the deadline would be missed, the Tier 0 path of section 5.2 runs first. Each result is a derived event with its producer and outcome (decisions.md C3).
4. Propose. Code turns the interpretation into a proposal by the table of capture-event-v0 §6.5: `add_item` with a due date resolved by code or `no_deadline`, priority `normal`, tags, provenance and spans; status waiting with `follow_up_at` when the item waits on someone; `file_document` for a dropped document after the document call; no op when the duplicate call says `same`. The duplicate call's other answers are checked by code before they become ops, because its relation offers too few choices and a small model then picks `update`: in one measured run the new item "the plumber sent his invoice for 625 dollars, check it before paying" came back as an `update` of the old leak-repair item, which would have produced an `update_item` with no changed dates and no `add_item`, so the new payment task would have vanished. So the relation gains a fourth value, `related`, which means `add_item` with a link to the candidate shown on the card. Code accepts `update` (an `update_item` on the candidate with the changed values) only when the item carries a time, amount or person that differs from the candidate's, and `done` (a `complete` on the candidate) only when the sentence holds a completion word ("paid", "sent", "done", "fait", "payé"); otherwise it falls back to `add_item` with "possibly related to" the candidate. Both rules join the fixtures, and the change to capture-event-v0 §6.5 is in section 13. New items carry placeholders, never ids (4.2). The target binder is the one the binder call chose from the closed list, turned into "not sure" when the code signals disagree (4.6). `binder_hint` is honoured only from an event in the app's own device folder that matches an XPC notice, where the person chose the binder, and never routes an item into a binder at disclosure `none` without the person picking it on the card. The proposal records `expect` fingerprints for every existing item it touches (4.6). A `sensitivity: private` capture is kept off the Today page and every MCP answer while it waits, and its proposal sets `redact: true` and a `kind` on what it creates (7.6).
5. File. On approval the guard applies the ops and files a per-binder copy of the capture, as capture-event-v0 §9 says: `captures/<captured_at>_<id>.json` in the binder's visible `captures/` folder, recorded with a `file_document` op, checked against the original's digest. The copy has `app_context` removed, and when the capture's items went to more than one binder its `text` is cut to the sentences this binder's items came from. Media are copied only when the person turned audio copying on, which is off by default for dictations and for meetings (capture-event-v0 §9). When a capture's items went to more than one binder, its audio is never copied into any binder; it stays in the app's capture store, because the whole recording would otherwise reach every binder and every binder's backup, across boundary 2. The full capture and the full interpretation stay only in the app's capture store. The filed copy carries the private marker when the capture was private (7.3). The visible `captures/` folder is a write beyond decisions.md F1 (section 13, item 36). The journal marks the event filed and records the op id that filed it in each binder.

A capture whose clerk pass fails follows the one retry policy of 3.4: one retry under a background budget, then it keeps its Tier 0 card and the Health page lists it as "the clerk could not read this". The M3 target is a proposal within a minute of a capture landing (decisions.md M3); the Health page shows the age of the oldest waiting event, so drift from that target is visible, with backfill from the importer counted apart (3.4).

What stays in the capture folder. The producer never deletes its files (decisions.md C2), and the consumer never writes into the folder. Left alone, the capture root becomes a plaintext pile that spans every binder, private captures and email included. It is backed up, may be synced (capture-event-v0 §5.1), and may be indexed by Spotlight (section 10), which works against boundary 2. Recommendation, settled together with capture-event-v0 §12 question 4: after an event is filed and a backup of the binder has succeeded, offer to move it to a 0700 archive under `~/Library/Application Support/Sprava/` that Spotlight does not index, or to delete it after N days, with the person's consent (section 13).

A binder restored to an older state. A real restore of a binder (`lifeproj restore`, which runs `cmirror pull` and then re-equips the folder; lifeproj-schema) puts back an older `catalog.json` and `ops.ndjson`, while the journal still says that later captures were filed there. At startup, and whenever a binder's log no longer contains the last op id the journal recorded for it, the runtime shows the "history went backwards" card of 4.5. When the person confirms a restore, it puts those captures back in the queue ("binder restored to an older state; N captures filed again for review") and moves the binder's high-water mark to the restored state. A restore onto another Mac also brings back an `owner.json` that names the old device; the takeover card of 2.3 handles it. A folder that vanished (for example after `lifeproj archive --purge-local`) is shown as "archived or moved", and its journal entries are kept. `lifeproj archive` without purge leaves the folder in place but moves its table in cmirror's config from `[projects.<name>]` to `[archived.<name>]`, which cmirror ignores (lifeproj-schema). So before each backup the runtime checks where the binder's key sits, and a binder found under `[archived]` is reported as "archived in lifeproj", its own state, never as a failing backup.

For the record, holos itself signals only through files: its recorder writes a status heartbeat every second and treats a status younger than 10 seconds as fresh, and its app polls folders every few seconds (holos-formats). The capture folder keeps that discipline: files, atomic renames, and a consumer that keeps its own record of which events it has handled.

## 9. Encryption and backup

This section defends boundary 6 and the "stolen backup" and "lost Mac" rows of the threat model.

### 9.1 What is encrypted where

At rest, binders are plain folders on a FileVault disk (FileVault is macOS whole-disk encryption). There is no app-level encryption in v0 (decisions.md A6). A plain folder is what lets lifeproj and terminal agents remain valid implementations of the format. Compartments against agents on a single-user Mac are a matter of surfaces and policy (sections 7.6 and 11), and the doctor checks that FileVault is on.

The offsite backup is ciphertext only, in the model cmirror already uses (web-localfirst-platform: the cmirror 1.0.0 source and the C2SP age specification):

- Each file is encrypted with age to the root recipient. age wraps a fresh 16-byte file key per file for each recipient and encrypts the content in 64 KiB ChaCha20-Poly1305 chunks.
- Blobs are named `blobs/<HMAC-SHA256(filename key, relative path)>.age`, so file names never appear in the cloud.
- The manifest, which maps paths to blobs with sizes, modification times and SHA-256 digests, exists only encrypted.
- Replaced and deleted blobs move to `_archive/<UTC stamp>/` with an encrypted snapshot of the previous manifest.
- Writes are temp, fsync, rename; one run at a time under a flock lease; a changed file is re-encrypted whole.

What a thief of the cloud folder learns: how many files there are, their encrypted sizes, and when things changed. Sizes say more than they seem: an audio blob's size reveals the length of a dictation (about 4 KB per second; holos-formats). What the thief does not learn: names or contents. Whether the thief can tell which binder is which depends on the layout. cmirror uses a separate project and cloud folder per binder (web-localfirst-platform), and then folder names and per-folder counts can identify binders. Sprava cannot rename them in v0: it writes nothing into the person's cmirror configuration (9.3), each project's `encrypted_dir` is set in that configuration, and lifeproj sets it to `<root>/<name>` for every binder it creates (lifeproj-schema). So every adopted lifeproj binder already has a cloud folder named after the binder, and cloud folder names may reveal binder names. What Sprava does about it: the doctor flags an `encrypted_dir` whose path contains `meta.name`; the registration help suggests an opaque `encrypted_dir`, such as a random id; if Sprava later keeps its own cmirror config (section 13, item 14), it writes random folder names itself. Renaming an existing mirror is a migration step the person runs.

Crypto-shredding has limits. cmirror moves deleted blobs to `_archive/`, and its `archive_retention_days` defaults to 0, which means keep forever (cmirror `config.py`). A wrapped binder key deleted on archive (9.2) would therefore survive in `_archive/`, where the root identity can still unwrap it. When per-binder keys arrive, wrapped binder keys are kept outside cmirror's archive, or the archive is pruned when a key is shredded. Shredding also does nothing for copies that were never encrypted (web-localfirst-platform): the capture root, Time Machine, the Spotlight index and the hub's slices keep what they hold. The same gap affects retraction of a capture (capture-event-v0 §12 question 21).

### 9.3 The backup job and recovery

The MVP calls cmirror where it is installed; a native implementation comes later and means either bundling the Go `age` binary or implementing the age format on CryptoKit (Apple's cryptography library) against the format's published test vectors, because no mature Swift age library exists (decisions.md A6; web-localfirst-platform). In the first release Sprava writes nothing into the person's cmirror configuration. Registering each binder, the capture root and `~/Library/Application Support/Sprava/` with cmirror is a manual step, a real hurdle for a non-technical person. The Health page shows plainly which adopted binders are not registered, and native backup is the first feature after the MVP (13).

Registering with cmirror also enrols a binder with lifeproj. lifeproj's teka registry is cmirror's own `config.toml`: every `[projects.<name>]` table is a live teka, and `lifeproj drain --all` drains every one of them and republishes those where a completion applied (lifeproj `registry.py`, `osavul.py` `drain_all`). The same holds for the capture root and Application Support: registered in the default config, they would appear in `lifeproj brief` as never-published tekas and be walked by `drain --all` as skipped. So the registration help tells the person to register those two folders in a separate cmirror config file, passed with `--config`, or to accept and know about that noise. So a managed binder registered in that file has a second drainer and a second publisher until lifeproj changes (section 11). The registration screen says so in plain words. Two ways out are open in section 13: the lifeproj change of teka-v0 §9.8, or a separate cmirror config file that Sprava keeps for managed binders and passes with `cmirror --config` (cmirror reads `--config`, then `$CMIRROR_CONFIG`, then `~/.config/cmirror/config.toml`; cmirror `config.py`), so they never appear in lifeproj's registry.

How Sprava calls cmirror (3.4, 3.5):

- With absolute paths for `cmirror` and `age`, resolved at setup and shown in Settings, an explicit `PATH`, and an explicit config path. A LaunchAgent does not read the person's shell profile, so variables such as `CMIRROR_CONFIG` set there are not in its environment; the config path is a Sprava setting pre-filled at setup from what cmirror resolves in the person's shell.
- Once per binder, with `--project <name>`, each with its own breaker and last success.
- After probing cmirror's lock (`~/.config/cmirror/backup.lock`) without holding it. A held lock is "skipped: another backup running", a state of its own and never a success.
- With no wall-clock limit. cmirror commits its manifest only at the end of a run, so a run killed before then starts over next time; a fixed 30-minute limit would kill a large first backup every night and it would never finish. Sprava sizes the run first with `cmirror status` (a dry run), then watches for progress and cancels only after a period with none: 15 minutes (proposed), 60 for a binder's first full run. cmirror encrypts each file whole, so progress counts the size of its temporary output growing as well as finished blobs appearing (3.4). A run cancelled this way records `no_progress` with the size of the largest file, so "too slow" never looks like an ordinary failure. The Health page shows the first run as "first backup in progress, 3.1 GB".
- After checking, before every run, that the identity file exists and matches the configured recipient, and that the SHA-256 of the `cmirror` and `age` binaries still equals the one recorded at setup in the sealed `settings.json`. A mismatch stops the backup and reports it; Sprava never runs a binary it did not set up.

What is backed up: every adopted binder folder including `.sprava/` and `captures/` (the op log, proposals, the slice key and filed captures are history), the capture root (audio exists only there until a capture is filed, and holos's own copies expire), and the app's state under Application Support (`shelf.json`, `settings.json`, `unfiled/`, `today/`, `capture/`, `mcp/clients.json`). The Keychain is never in a backup; a restored Mac creates a new runtime key after the person confirms it (4.1), the person re-confirms each brain's record in the app and re-registers it, and each binder needs the takeover card (2.3). Sprava's own rotated logs are not backed up (2.3). The index can be rebuilt and should be excluded: cmirror supports per-project `excludes` with shell-glob patterns that also match any path under a matched folder (cmirror `config.py`, `scan.py`), so the pattern `index.sqlite*` covers the index and its `-wal` and `-shm` files. Sprava does not write cmirror's configuration in the first release, and the binders already registered there carry no such exclude, so adding it is part of the person's manual registration step, and the doctor checks it. Without it the index is backed up while open, re-encrypted whole on each run, and each replaced copy is kept in `_archive/` (9.1).

Recovery is practiced, not assumed:

- At setup the app insists on the passphrase recovery copy and will not mark backup "configured" until it exists.
- The setup screen, and later the Health page, offer a restore drill: restore one binder into a temporary 0700 folder that Spotlight does not index, compare its catalog hash with the live one, check that its `owner.json` and seals would lead to the takeover and "sealed by an earlier key" states a real restore onto a new Mac would show (2.3, 4.1), then delete the temporary copy.
- `cmirror verify` runs weekly as part of the backup job.
- The Health page checks that the identity file exists and matches the configured recipient. A last success older than 48 hours is amber and older than 7 days red (proposed), per binder, counted as 3.4 says from the latest of the last success, the last wake and the runtime's start. This is the one statement of the backup thresholds; the manifest will carry them.
- After a real restore, the runtime notices that a binder's log went backwards and queues again the captures filed after the backup (section 8).

## 11. Hub coexistence

This section defends boundary 2 at the spool, where a binder's items reach another program. Binders that Sprava manages keep talking to the existing hub through the spool, with lifeproj's semantics plus the recurrence rule of teka-v0 §8.3 (decisions.md A8, F8; teka-v0 §8). Where this section departs from lifeproj's exact semantics, it says so, and section 13 lists each departure as a refinement for the author.

One publisher and one drainer per binder (teka-v0 §8.1). Today's lifeproj would be a second one for every managed binder, on a schedule:

- lifeproj's registry is cmirror's `config.toml`, and the hub's cron runs `lifeproj drain --all` over every registered teka, then republishes each one where a completion applied (lifeproj `registry.py`, `osavul.py` `drain_all`). A binder registered with cmirror for backup (9.3) is therefore drained twice. If lifeproj writes the catalog and acknowledges the outbox between the guard's read and its rename, the check-off is lost from both places and the item comes back open (4.5). The lock and the compares before rename narrow that window; only lifeproj staying away closes it.
- The manual stamped into a lifeproj binder tells every terminal agent to run `lifeproj drain` first and `lifeproj publish` last in each digest (lifeproj `templates.py`; lifeproj-schema: the digest ritual). lifeproj's slice ignores `meta.disclosure` and `dismissed`: it publishes the full title unless the item itself sets `redact` or `slice_title` (lifeproj-schema). So a binder the person set to `title`, `kind` or `none` gets a full-title slice again after the next terminal digest or fleet drain, and the hub pushes those titles to Google Tasks. lifeproj's drain also closes a recurring item for good.

So, as long as lifeproj can still publish a managed binder, its disclosure is unenforceable at the hub, and the design says so (section 10). The fix is the lifeproj change listed in teka-v0 §9.8, with two refinements this design asks for (section 13, item 31):

- The refusal is keyed on adoption, not on migration. A binder is stamped `meta.format: "teka"` only by `migrate`, once every item satisfies the v0 rules (4.7; teka-v0 §9.4 step 6), and a binder with one item that never gets a date stays "adopted, needs migration" indefinitely while Sprava already publishes and drains it. So lifeproj refuses when the binder has `.sprava/ops.ndjson`, the mark of an adopted binder, as well as when `meta.format` is `teka`.
- The refusal is a success-path no-op. The manual's ritual starts with `lifeproj drain` and ends with `lifeproj publish`, and nothing edits the manual (decisions.md F1). A non-zero exit would fail every terminal digest at its first and last step, and agents tend to "fix" the catalog until a command passes. So lifeproj prints one line, "this teka is published and drained by Sprava; nothing to do", and exits 0, as it already does when the spool is absent (test `test_publish_noop_when_spool_absent`). Non-zero exits stay for real errors.

The change also takes the binder's lock and leaves such a binder out of `drain --all`. It is a prerequisite for decisions.md A8 (section 13). Until it ships:

- an adopted binder that is still in lifeproj's registry keeps disclosure `full`, and the app refuses `dismiss` and `recurrence` on it and says why (teka-v0 §8.1);
- while it is in lifeproj's registry, Sprava publishes the byte-compatible lifeproj projection for it: no aliases and no v1 fields, so two publishers do not flip the same item's slice id back and forth (below);
- the doctor flags every managed binder listed under `[projects]` in cmirror's config: "drained and published by lifeproj too";
- before each publish, and in the doctor, Sprava compares the slice on disk with the hash of the slice it last wrote (`.sprava/cursors.json`) and alarms "slice overwritten by another publisher" on a mismatch;
- the doctor reports each managed binder whose manual still tells agents to run `lifeproj drain` or `lifeproj publish`, and the app offers a Sprava section to paste in (section 12).

Spool root. lifeproj resolves it as `$OSAVUL_SPOOL`, else `$XDG_DATA_HOME/osavul`, else `~/.local/share/osavul` (lifeproj-schema). The runtime is a LaunchAgent and does not read the person's shell profile, so it cannot rely on those variables, and any program that can set the runtime's environment could redirect where plaintext slices go. So the spool root is resolved once at setup, from the value lifeproj resolves in the person's shell, stored in the sealed `settings.json`, shown on the Privacy page and the Health page's hub line, and changed only from the app's own window (2.1). "Granted" means the root exists; Sprava creates `inbox/` but never the root, and a missing root means "not publishing", with a one-line note. The root, `inbox/` and `outbox/` must belong to the person and must not be writable by others, and neither folder may be a symbolic link (teka-v0 §8.1). Whether the hub actually reads the slices Sprava writes is not verified (critique.md: hub contracts not researched). The recency of outbox files is at best a weak hint, because the hub writes an outbox only when it has completions.

- Publish: `inbox/<meta.name>.agenda.json`, written through a same-folder temp file and rename. The slice object is `{teka, lifecycle, active_chapter, active_chapters, generated, items}`; each item has exactly the nine fields `id, title, status, priority, due, no_deadline, tags, waiting_on, link`; ids are prefixed `<teka>-` once. `slice_title`, else "[redacted]" when `redact` is true, sets the title, and `redact: true` masks `waiting_on` as "[party]" whatever the title (lifeproj `osavul.py`, `project_slice`). The slice comes from the slice projection module with the binder's disclosure applied, and is validated before it is written, as lifeproj does regardless of schema version (lifeproj-schema).
- Aliases. teka-v0 §5.5 and §5.6 replace the id of a redacted item that is not in the recommended form with an alias, `<teka>-r-` and 12 hex digits of an HMAC of the raw id, at every disclosure level, `full` included; at `title` and `kind` every id not in that form is aliased, redacted or not. The key is `.sprava/slice-key`, made on first publish, which is history and cannot be rebuilt (2.3). lifeproj publishes `<teka>-<raw>` for the same item. So while lifeproj can still publish a binder, Sprava publishes without aliases, as the item above says, and switches to aliases only once it is the sole publisher. The drain resolves both forms.
- Closures reach the hub. decisions.md F5 carries closures in the slice's `closed[]` "so the hub learns of closures", but the v1 fields sit behind a per-spool setting that stays off until the hub's readers are checked (below and item 35). With `closed[]` off, an item closed in the app would reach the hub only as an id that disappeared, and how the hub and its Google Tasks mirror treat a vanished id is unverified (critique.md). lifeproj's convention is the opposite: a done item appears once in the slice and is then dropped (lifeproj `templates.py`; lifeproj-schema: the done-appears-once rule). So until `closed[]` is switched on, Sprava publishes each item closed since the last publish once in `items[]` with `status: done`, which the nine-field slice and lifeproj's validation allow and `lifeproj brief` skips, and then drops it. This refines decisions.md F5, which bans `status: done` in a managed catalog; the slice is not the catalog (section 13).
- Disclosure `none`. A binder at `none` publishes nothing, and setting a binder to `none` removes its existing `inbox/<meta.name>.agenda.json` in the next publish job, as teka-v0 §5.5 says ("an existing slice file is removed"). A binder that published before, as every lifeproj binder did, would otherwise leave its last full-title slice in the spool for the hub to keep rolling up and mirroring. The `set_disclosure` card says that what the hub and Google Tasks already hold is not recalled (teka-v0 §5.5). The alarm "slice file present" fires only when a slice reappears after that removal.
- The v1 fields. decisions.md F8 allows additional fields (`format_version`, `closed[]`, `kind`, `follow_up_at`) that a hub may ignore. `lifeproj brief` tolerates extra keys (it reads items with `.get`), but whether the hub's own readers (the web lens and the Google Tasks mirror) do is unverified (critique.md; teka-v0 §8.4). So the v1 fields sit behind a per-spool setting, off until the hub is checked.
- Drain: `outbox/<meta.name>.intake.json`. Only `completions[]` are read; an id matches the raw catalog id, `<teka>-<raw>` or an alias; only `done` and `dropped` apply; each applied completion becomes a `complete` or `drop` op with actor `external`, origin `spool-outbox`, and the completion's `source` (teka-v0 §8.3); the catalog is written before the outbox is acknowledged; unknown completions linger; the `items[]` stub is preserved; nothing is republished when nothing applied (lifeproj-schema: drain semantics). A `done` completion on a recurring item completes that occurrence and advances `due` (teka-v0 §8.3), where lifeproj closes the item.
- The acknowledgement is a compare-and-swap. The hub, not the binder, writes the outbox, and it does not take `.teka.lock`, so the binder's lock does not protect that file. lifeproj's `_drain_teka` reads the outbox once and later rewrites it from that in-memory copy, even when nothing applied but completions or items remain (`osavul.py`, read 2026-10-06), so a completion the hub appends between the read and the rewrite is erased, and the phone check-off is lost. Sprava's outbox is also never empty for long: held completions, unknown ids and ids already closed stay in it. Copied exactly, Sprava would rewrite it every 5 minutes. So Sprava never rewrites the outbox when nothing applied. When something did, it re-reads the outbox just before the rename, removes only the applied ids from that fresh copy, and retries when the file's hash changed since the drain read it. This is a deliberate departure from lifeproj's exact semantics, a refinement of decisions.md F8, and the same change is asked of lifeproj in teka-v0 §9.8 (section 13).
- The drain is the deliberate exception to boundary 3. Completions skip the review queue because they are the person's own check-offs made on the hub or the phone, and lifeproj applies them the same way. The outbox is a plain file, though, and any program running as the person, or a brain with file tools, could write completions into it. So the channel is named and limited. The spool folders must pass the ownership checks above. The Health page shows a "closed from the hub" list for the last 7 days with one-click Undo (a `reopen`, 4.4) and a count. A drain that looks unusual is held as a card before anything is applied: more than 10 items at once (proposed), or an id that matches no slice id published for that binder in the last 30 days (proposed). Published ids come from Sprava's cursor and from the slice on disk, whoever wrote it, so the first drain after adoption, when lifeproj wrote the last slice, is not held by mistake. A held completion stays in the outbox, unacknowledged, until the person decides, so the rule that unknown completions linger still holds. Holding completions at all is a third departure from lifeproj's drain, which applies them with no approval step (decisions.md F8; teka-v0 §5.1, §8.3), so it is a refinement for the author (section 13). It protects only once lifeproj has stopped draining the binder: until then lifeproj applies the same completion without the hold.
- Completions for items already closed in Sprava. Once Sprava is where most items are closed, a check-off on the hub or the phone for an item the person already closed in the app is routine. lifeproj's rule skips it as "already gone" and never acknowledges it, so it would linger forever and the pending count would never clear. The Health page counts these apart from truly unknown ids. Acknowledging them, as a no-op recorded in `jobs.log`, would be one more departure from lifeproj's exact semantics, so it is proposed as a refinement of decisions.md F8 (section 13).
- Recurring items and the hub. A recurring item keeps the same slice id across occurrences. If the hub writes completions idempotently by id over time, the second occurrence could never be checked off from the hub or the phone. The hub's code is not verified (critique.md: hub contracts not researched). Before recurrence ships in a binder the hub reads, this is checked against the hub; occurrence-qualified slice ids such as `<id>@<due>`, matched by the drain, are the fallback (section 13).
- Daily beat: Sprava republishes each managed binder once a day even without change. `lifeproj brief` flags a slice older than 7 days as stale (lifeproj `brief.py`, `STALE_DAYS`; lifeproj-schema); whether the hub's own views do the same is unverified (critique.md). With a daily beat, a stale slice from a Sprava-managed binder in `lifeproj brief` means "Sprava has been down for a week". That alarm is reliable only while Sprava is the binder's only publisher.
- `lifeproj brief` matches registry keys against slice file names and skips any other slice (lifeproj `brief.py`, `collect`). A binder created in Sprava and not registered with cmirror therefore publishes a slice that `lifeproj brief` never shows. The Health page says so next to "not registered for backup".

Inside Sprava, the Today page replaces the hub's web lens over time (decisions.md A8). It reads every binder through the slice projection, keeps one bucket taxonomy (decisions.md F4: the hub's "This week" is "Next 7 days", and its "Waiting/blocked" splits into Nudge and Waiting), keeps GTD contexts and the "what can I do right here" question, and applies the op mapping of section 4.3, with one owner of planning metadata per binder during the transition. An absent binder is invisible, never an error, and the error channel logs file names and parse errors only (existing hub design; 3.7). Ask-through, the hub lesson about answerability, is answered inside the app by opening the binder from any card, and for brains by `get_item` with history within scope (HANDOFF).

The Google Tasks mirror stays on the hub during the transition (decisions.md A7, M2). The briefs lane stays an informative annex and a hub feature; in Sprava a readable document is a document in the binder, shown in the app (decisions.md F8). The spool remains as an interop lane after the web lens retires, because a sandboxed terminal session can still publish into it.

## 12. Documentation from code and the doctor command

A capability manifest is generated at build time from the code: the job table with cadences and budgets, the op vocabulary with its JSON Schemas, the MCP tools, resources and prompts with their annotations and limits, the SHA-256 of the tool catalog, the outbound inventory, the file layout, the heartbeat schema and the health fields. The mechanical pages of the docs (`docs/generated/`) are rendered from the manifest, and the build fails when the committed pages differ from the rendered ones (decisions.md A9). The manifest and the rendered pages also ship inside the app bundle, so on an installed Mac the doctor compares the running build with the manifest of its own bundle. The build also fails on any non-ASCII byte in a tool description (7.7). Prose docs cite the manifest by key instead of restating numbers. This v0 draft is the exception while no manifest exists: its numbers are the source for now, and each will be replaced by a manifest key when the manifest is built. The second design-skeptic pass found the draft already disagreeing with itself in two places (the backup thresholds and the outside watcher's condition), the early sign of docs drift that the manifest exists to stop.

`sprava doctor` (also a Run Checks button on the Health page) checks reality against the docs and the format, and reports. It fixes nothing by itself except offering to rebuild derived files (index, dashboard, caches); repairs to a catalog arrive as proposals in the queue. It runs no hook or script found in any binder (decisions.md F9) and takes no lock. Checks, grouped:

- Runtime: registered and enabled; the registered helper path equals the running bundle, which is not translocated and not on a disk image; the lease held by the heartbeat's pid, whose start time matches; heartbeat age and validity against Appendix A; the outside watcher ran recently (`runtime/watch.json`); breaker states, and jobs that caused watchdog restarts; wedged jobs; restart count; refused duplicate starts; more than one installed copy of the app (3.1); notifications allowed (3.7); the runtime key readable (4.1); `settings.json` and `shelf.json` seals verify, else tampering is reported and publishing and backup pause on the last sealed values; disk space used by Sprava's own state and its growth (2.3); socket path length and mode; no TCP port open by any Sprava process; the absolute paths of `cmirror` and `age` exist and their SHA-256 matches the one recorded at setup.
- Mac: FileVault is on; whether Time Machine includes binders, the capture root and Application Support, and whether its disk is encrypted; which binders Spotlight indexes (section 10; detection is a spike).
- Logs: Sprava's own files (`jobs.log`, `lease-refusals.log`, the audit logs, the heartbeat, `doctor.json`) contain no binder title, no `meta.name` and no open item's title (3.7).
- Model: availability and reason; context size; locales; prompt versions tested against the current model version with the fixture set of 5.3.
- Binders: `meta.name` equals the folder name (decisions.md F6) and the cmirror registry key, the third name lifeproj assumes equal (lifeproj-schema); the catalog validates for its declared version; the hash chain is intact, every line's seal verifies, and the log is not shorter than the binder's high-water mark (4.5); external edits since the last run, and approved changes they undid; records needing attention; torn tails repaired; leftover temporary files `.catalog.json.sprava-*.tmp` removed (4.2); proposal files the runtime did not write, or whose digest changed; proposals pending, older than 7 days, or needing a look; index freshness; `DASHBOARD.md` rewritten by an outside tool since the last regeneration; the binder is not in a sync location and its owner record names this Mac, else the takeover state (2.3); the binder lock held by another program, with the holder; `.git/` present (tolerated, decisions.md F12); hooks or scripts present (ignored, never executed); `.claude/settings.json` route hooks present, and a plaintext lifeproj request log under `~/.local/share/lifeproj/` (both reported, section 10); a manual (`CLAUDE.md`, `AGENTS.md`) that still tells agents to edit `catalog.json` by hand or run `lifeproj drain` or `lifeproj publish` (the app offers a Sprava section to paste in; it never edits the manual, decisions.md F1); documents' `path` values inside the folder and existing.
- Captures: capture root reachable, owned by the person and not writable by others, and not in a sync location unless it is an encrypted opt-in root; every device folder has a registered producer, and none is a symbolic link; events in the app's folder without a matching XPC notice; quarantine count; captures filed by Tier 0; inputs that crashed a stage twice; oldest waiting event.
- Hub lane: spool root as stored in settings, granted, and owned by the person; slice fresher than 24 hours; the slice on disk equals the one Sprava last wrote; managed binders still listed under `[projects]` in cmirror's config (drained and published by lifeproj too); pending completions, split into unknown, already closed and held; a slice whose name matches no managed binder; a binder at `none` whose slice reappeared after removal.
- Backup: identity file present and matching the recipient; per binder the last success, a first backup in progress, or skipped runs; last weekly verify; adopted binders not registered with cmirror; binders whose key moved under `[archived]` in cmirror's config; an `encrypted_dir` whose path contains `meta.name` (9.1); the recovery copy made and not stored beside the blobs; the `index.sqlite*` exclude present in each binder's cmirror project, which the person adds by hand (9.3).
- Brains: every client record's seal verifies; clients that keep their token in a plain config file (note) or a `.mcpb` sensitive field (information); a Sprava token, recognized by its `sprava_ct_` prefix, found anywhere other than a client's server settings, such as a shell profile or a shell history file (warning); a Claude Code entry at project scope (warning); tokens expiring within 14 days, when an expiry was set; clients with no call in 90 days (suggest revoking); the tool catalog hash in the running build equals the one in the manifest shipped in the bundle; no client over budget today.
- Outbound: the configured channels equal the inventory of section 10.
- Docs: the manifest shipped inside the bundle matches the running build; every job, tool and outbound path in the manifest has a doc line; every doc line has a manifest key. Repository pages are checked at build time, not on an installed Mac.

The report is a JSON file plus a readable page, each line "ok", "note" or "fix", and its finding count is the last line of the Health page.

## 13. Open decisions, with a recommendation each

The author decides. Items marked "refinement" change the wording of a decision in `decisions.md` and need the author's acceptance; items marked "spec" ask for a change in `docs/spec/teka-v0.md` or `docs/spec/capture-event-v0.md`; items marked "spike" need a short experiment because the research did not cover them.

1. MCP in the MVP (decisions.md M1, open). Recommendation: yes, reads and proposals only, Claude Code first, because the author drives binders with Claude Code today and the shim and listener are small once the guard and the slice projection exist. `docs/mvp.md` narrows this for the MVP to proposing only, with `list_binders` and `get_proposal` and no other read tool (mvp.md section 8, question 1; item 46).
2. MCP server stack (decisions.md A10). Recommendation: a hand-rolled dual-era JSON-RPC server in Swift, with a conformance suite run against Claude Code (modern era) and a 2025-11-25 client (legacy era). No Python or Node sidecar inside the app.
3. Era sequencing, as an option only. Build the 2026-07-28 era first and the legacy era second, before any release that names Claude Desktop or Gemini CLI as supported. Recommendation: allowed as a build order; the dual-era target of decisions.md A4 stays intact.
4. Token delivery (decisions.md A4, followed as written). Recommendation: the token lives with the client, in the environment entry of its own server settings, or in a `.mcpb` field marked sensitive where the client offers that (7.5). The first draft's refinement, a token in Sprava's Keychain fetched by the client id in the shim's arguments, is withdrawn: any program running as the person could launch the genuine shim with any client id. Say plainly, in the app and in the docs, that the token gives attribution, scope against an honest client, budgets and revocation, and does not authenticate a client against other code running as the same user. Alternative kept open: a Keychain item that asks for Touch ID or the password once per session per client.
5. Peer checks on the socket. Recommendation: reject any peer with a different user id from the first build. The code-signature check of the peer is a diagnostic only ("the peer is our shim"), never a defence, because an attacker would launch the genuine shim (7.2). Spike whether it works at all.
6. Lease and launch. Recommendation: the runtime refuses to take the lease unless launchd started it for Sprava's label (a successful MachService check-in); a development build runs only with `--dev`, its own folder and its own socket; `KeepAlive` true and a refused copy exits 0, so launchd keeps probing every 10 seconds while an old copy finishes exiting (3.2). Spike: confirm that only the launchd-managed instance can check in the MachService name.
7. Heartbeat, watchdog and the outside watcher. Recommendation: a plain timer beating every 30 seconds and at once on wake; amber at 2 minutes, red at 5 minutes (decisions.md M3), graded from the later of the last beat and the last wake, with "waking up" for 60 seconds; the watchdog measures awake time only (`SuspendingClock` or `mach_absolute_time`) and exits after 120 seconds without a tick or 10 minutes with a wedged job, recording the culprit job so its breaker opens after 2 such exits (3.4); a second tiny launchd job, `sprava-watch`, on four `StartCalendarInterval` entries, that checks the pid and its start time, grades the beat from the later of `beat_at` and `kern.waketime`, waits 2 minutes after a fresh wake, and notifies at most once a day when the beat is older than 15 minutes, the person did not turn background work off, and the app is not running (3.3). Say plainly that it shares the runtime's registration and cannot catch a switched-off or moved bundle; the app and the 7-day stale flag catch those. Add the outside watcher to the operability criterion in decisions.md M3 (refinement).
8. Where filed captures live. Recommendation: follow capture-event-v0 §9: a per-binder copy in the binder's visible `captures/<captured_at>_<id>.json`, recorded with a `file_document` op, without `app_context`, with `text` cut to that binder's sentences, and media only when the person turned audio copying on; a capture whose items went to more than one binder keeps its audio in the app's capture store (section 8). The first draft's `.sprava/captures/` is withdrawn, which settles capture-event-v0 §12 question 23. The visible folder is a write beyond decisions.md F1 and joins item 36. Spec: teka-v0 §9.7 lists `captures/` among the folders an implementation may write.
9. Spec: where planning metadata lives. This draft follows teka-v0: `contexts`, `estimate_min` and `dismissed` are item fields of a managed binder, changed by ordinary ops, and only `importance` and the global context labels sit in the annotations store keyed `teka:id` (4.3). Recommendation: follow teka-v0, and settle `importance` and the binder default context with teka-v0 §12.
10. Spec: what this design needs from teka-v0. The `reopen` op that re-adds a closed item under a new id with `provenance.reopened_from` (teka-v0 §6.3, §6.10, as drafted), never a plain reopen that reuses a closed id against decisions.md F2; placeholder ids minted at apply time (teka-v0 §5.6); a `withdrawn` proposal state, so a brain's withdrawal is not recorded as a rejection (4.6); a named `expect` field on proposals (4.6); an optional `seal` field on op lines that other implementations ignore (4.1); `documents[].sensitivity` with the value `private`, honoured by every reader, whose removal or lowering is a widening change (7.3, 4.5); two runtime records, `takeover` (2.3) and `rekey` (4.1); `.sprava/owner.json` in the table of teka-v0 §7.2, which requires every unlisted file there to be rebuildable, and an owner record is not; an actor field for the MCP client's name on `brain` ops, because teka-v0's `actor.client` names the implementation (4.1); a seal that covers the binder id, a key id and the previous seal (4.1); a proposal body folder `.sprava/proposals/<id>/` for a brain's document (4.6); and, in §6.5 and §9.7, the rule that nothing a proposal carries reaches the binder's visible folders before approval (7.3). Recommendation: settle all of them before the guard is written.
11. External edits. Recommendation: record and continue when the catalog still validates; when it does not, split by kind: a record that breaks lifeproj's v2 rules needs attention on its own and blocks only ops that touch it, while a record that misses only a v0 addition blocks nothing and is repaired by a card, or, for purely mechanical repairs, by one undoable `import` batch after a 10-minute quiet period, never in the middle of a terminal agent's digest (4.5, teka-v0 §6.7). An outside edit that undid approved changes gets a card with one-click re-apply (4.5). A widening privacy change made outside the app waits for a card (the privacy ratchet). Spec: teka-v0 §6.5 lists mechanical steps applied without a proposal only at adoption, and teka-v0 §6.7 step 7 offers every repair after an outside edit as a proposal; the quiet-period `import` batch needs both to change, or it becomes a card.
12. Accepted risk: concurrent writes by programs that skip the binder's lock. Sprava takes `.teka.lock` and compares the catalog again before its rename (4.2), and once more after the log flush, which narrows the window to the moment between the last hash and the rename. The chain detects an outside write made between two of Sprava's writes; it cannot detect a lost update inside one write. Recommendation: accept the remaining risk for a person typing in a text editor, say so in the spec, and do not accept it for lifeproj's scheduled drain, which is item 31.
13. Backup in the MVP. Recommendation: call cmirror where installed, once per binder with `--project`, with absolute paths for `cmirror` and `age`, no wall-clock limit but a no-progress cut-off, and a lock probe that records a skipped run as skipped (3.4, 9.3); show a plain "install the backup tool" step otherwise, and make native backup the first feature after the MVP, implemented on CryptoKit against the age test vectors, because bundling the Go binary complicates notarization and licence review.
14. Accepted risk: registering binders with cmirror by hand. It is a real hurdle for a non-technical person, and registering a binder in cmirror's default config also registers it with lifeproj's fleet drain and publish (9.3). Recommendation: accept the manual step for the first release (decisions.md A6), show unregistered binders plainly on the Health page (3.6, 9.3), and warn on the registration screen that registration enrols the binder with lifeproj. Option: Sprava keeps its own cmirror config for managed binders and passes it with `--config`, so they stay out of lifeproj's registry; the cost is that `lifeproj brief` then skips them (section 11).
15. The index in backups. Not settled by Sprava alone: cmirror supports per-project `excludes` with shell-glob patterns (cmirror `config.py`, `scan.py`), so `index.sqlite*` would exclude the index with its `-wal` and `-shm` files, but Sprava writes nothing into cmirror's configuration in the first release and the binders already registered carry no such exclude. Recommendation: the person adds the exclude as part of the manual registration step, the registration help shows it, and the doctor checks it (9.3).
16. Binders with disclosure `none` in the clerk's filing list. Recommendation: follow capture-event-v0 §6.4 step 2: such a binder is left out of the binder call unless the person opts it in, and an opted-in one is offered under an opaque label such as `binder-3` with a neutral one-line description the person wrote. Say plainly that items for such a binder normally land in "not sure" and the person picks the binder on the card (5.4). The first revision's rule (always offered under a bare label, cited to step 1) is withdrawn: a bare label carries no meaning the model could match, and step 1 has no binder list.
17. Logging policy. Recommendation: as in 3.7: `os_log` private marks with a build-time lint, an opaque binder id instead of `meta.name` everywhere, no title, folder name, file name or content in any log, error, notification, crash message or the heartbeat, and the doctor searching Sprava's own files for titles and names.
18. Private captures after filing. Recommendation: set `redact: true` and a `kind` on what a `sensitivity: private` capture creates, and mark the filed capture and its documents private, so cross-binder surfaces show only the kind and no read path returns the text (capture-event-v0 §3.3; 7.3). The person can change it on the card.
19. Tier 0 capture proposals and the app's own captures. Recommendation: yes to both: a code-built "not sure" proposal whenever the model cannot run or the minute would be missed (5.2, 3.4), and typed notes and dropped documents through the capture folder, with the app read-only while the runtime is down (2.1).
20. Confirmation in conversation for brains. Recommendation: ship the tool-result text first; add the optional elicitation question only on modern-era connections and only for a client whose sealed record has the elicitation flag on, off by default and turned on per client type once that type is tested (7.4). A declared `elicitation` capability is not enough, since hosted Claude and Gemini CLI cannot render it and Cowork hangs on it (7.4, 7.8).
21. Claude Code's `anthropic/requiresUserInteraction` on `propose_ops`, which would make Claude Code ask before every submission. Recommendation: not set in v0, because a proposal changes nothing and approval is in the app; offer it as a per-client setting if the person wants the extra prompt. Offer it separately on `read_document`, suggested for binders that hold other people's documents (7.3).
22. Client token lifetime and budgets. Recommendation: no forced expiry by default, because it would rebuild the 7-day OAuth lesson and protects little on one Mac; an optional expiry per client, with a notification 14 days ahead and a warning line in every tool result; a client idle for 90 days is suggested for revocation; 60 calls per minute, 2,000 per day and 50 MB of results per day, with a breaker per client (7.5).
23. Minimum hardware and the clerk's release gate (decisions.md P2). Recommendation: M1 and later, design for 4,096 tokens, and gate per model variant, never per chip: "a Mac that reports the Core model and 4,096 tokens", which includes M3 or later Macs with 8 GB (5.1). Refinement: decisions.md P2 words the split by chip (M1 and M2 versus M3 or later with 12 GB); it should name the variant and memory. Before the clerk ships, run the invented English and French fixture set through the Swift clerk itself, never `fm`, on such a Mac, with the runtime classified Background, measuring recall, tokens and latency per call against a pass bar, including the read-only context-size probe and the meeting bound of 5.3; repeat after every model update. Adapters are obsoleted in macOS 27, so the levers are instructions, window size, task splitting and code checks. If the Core model fails the bar, the clerk ships on such Macs with smaller windows, or as suggestions beside the Tier 0 card, or off, and the release notes say which (5.3; capture-event-v0 §10.5).
24. Background rate limiting of the on-device model. Recommendation: a burst test from the runtime, on battery and under `ProcessType` Adaptive while classified Background, before the MVP ships, which also measures the clerk's time per window and the beat's jitter (3.1, item 39 f); the code handles `rateLimited` either way (5.4).

## 14. Design-skeptic pass

The first pass. On 2026-10-06 four skeptics read the first draft, each through one lens, and checked its claims against the research digests, the lifeproj and cmirror source, `man launchd.plist` on macOS 27, and new `fm` runs on invented text. The lenses were: operability (what stops at 3 a.m. and who notices), security and privacy (who can lie to the runtime, and what leaks), the clerk's budget (does the call plan fit 4,096 tokens and one minute), and the format and the hub (does Sprava coexist with lifeproj and the hub without losing data). They raised 69 findings, 6 of them critical. Every critical and major finding changed the design; most minor ones did too.

The serious findings, and what changed:

- A second writer on a schedule (critical, raised twice). lifeproj's registry is cmirror's config, so registering a binder for backup enrols it in `lifeproj drain --all`, and the binder's manual tells agents to run `lifeproj publish`. That meant two drainers, a lost-update race that the hash chain cannot see, and slices that ignore disclosure. Changed: the guard takes the binder's lock and compares before its rename (4.2), the chain's limits are stated (4.5), one publisher and one drainer per binder is a prerequisite with a lifeproj change (section 11, item 31), and the doctor and the publish job detect the second writer.
- Undo of a closure (critical). A plain `reopen` would reuse a closed id, which decisions.md F2 forbids and lifeproj's publish rejects. Changed: `reopen` re-adds the item under a new id (4.3, 4.4).
- The client token (critical). With the token in Sprava's Keychain and the client id in the shim's arguments, any program running as the person could act as any client. Changed: the token lives with the client, as decisions.md A4 says; the token is described as attribution and scope, not authentication; scope changes only from the app and client records are sealed (7.2, 7.5).
- The first draft's long extraction call, J1 (critical). Answers grow with input, so the 800-token cap and the 1,200-word chunk did not hold. Changed: the call plan is capture-event-v0 §6.4, with fixed windows, a per-item answer reserve, greedy sampling everywhere, and a fixture gate on the 3B model (5.3). (The first revision also put the binder choice into the extraction call; the second pass found that the spec does the opposite, and the binder is now its own call.)
- Silence inside and outside the process (major). Nothing watched the runtime when the app was closed; sleep looked like a stall; a blocked job looked healthy; one bad input could crash-loop the process. Changed: the outside watcher, a clock that stops during sleep, per-job staleness and the "wedged" mark, and the poison-input rule (3.3, 3.4).
- "0 done, 0 errors" again (major). cmirror exits 0 when another run holds its lock, commits only at the end of a run, and cannot find a Homebrew `age` from a LaunchAgent. Changed: lock probe, a skipped state, progress-based cancelling, per-binder runs and absolute paths (3.4, 3.5, 9.3).
- The one-minute target (major). It counts from landing, so queue wait counts. Changed: a code-built card first when the minute is at risk, finished windows never thrown away, backfill counted apart (3.4).
- Forged inputs (major). Capture events, proposal files, op-log lines and outbox completions can all be written by any program running as the person. Changed: registered producers per capture folder, containment rules on capture files, sealed log lines, proposals trusted only when the runtime wrote them, the drain named as the one exception and watched, and a privacy ratchet for widening changes made outside the app (4.1, 4.5, 4.6, section 8, section 11).
- Read paths that skipped the projection (major). History, search and filed private captures could return what disclosure hides. Changed: every read goes through the projection, and private documents carry a marker (7.3).
- Where binders live (major). Sync folders, Time Machine and Spotlight move or expose plaintext. Changed: v0 refuses synced binder folders, an owner record per binder, new rows in section 10, and spikes for detection and privacy permissions (2.3, section 10).
- Launch and restart (major). A hand-started copy could hold the lease where the app cannot reach it, Restart was unverified, and a moved or translocated app breaks registration. Changed: only a launchd-started runtime takes the lease, a `--dev` mode, a build check, and spikes for Restart and bundle location (3.1, 3.2, 3.3).

Concerns kept open rather than designed away, because they touch a decision: acknowledging completions for items already closed (item 33, decisions.md F8), the owner of planning metadata during the transition (item 32, decisions.md A8), and the three writes teka-v0 makes beyond decisions.md F1 (item 36).

The second pass, the same evening, read the revised draft through the same four lenses and checked it against `man launchd.plist` and `man 4 unix` on macOS 27, the lifeproj and cmirror source, the two format drafts, and new `fm` runs on invented text (greedy, with the published model schemas and realistic instructions). It raised 72 findings, 1 of them critical and 43 major. Every critical and major finding changed the design, and so did every minor one; none was rejected. The serious findings, and what changed:

- A brain's document in `intake/` (critical). `intake/` is the terminal agent's drop zone, so a pending, possibly injected, document would be filed by the next terminal digest without approval. Changed: the body stays inside the proposal until approval, then goes straight into a document folder (7.3, 4.6, items 36 and 42).
- What the outside watcher can see (operability). It shares the runtime's registration, so it cannot see a switched-off or moved bundle, and it fired at the moment of wake with no record of sleep. Changed: its real coverage is stated, the shared failures are caught by the app and the 7-day stale flag, and it checks the pid and `kern.waketime` before deciding (3.3, 3.8).
- Silent alarms and restart loops (operability). Notifications might not be postable; breaker state lived only in memory, so a job that wedged every run would restart the process forever; a blocking lock, an XPC request without a timeout, or an unreadable Keychain key could each hang approvals with no culprit named; logs had no retention. - Who and what can lie to the runtime (security). Proposal content, the app's own capture folder, `settings.json` and `shelf.json` could be rewritten by any same-user program, a truncated log could undo a privacy narrowing, and documents were parsed in the process that holds the key. Changed: proposal digests checked at approval, XPC notices for the app's captures, sealed settings with binary hashes, privacy values and a high-water mark kept outside the binder, chained seals with key ids and rekey checkpoints, and a sandboxed extraction helper (2.1, 2.3, 4.1, 4.5, 4.6, section 8).
- Privacy leaks (security). `documents[].sensitivity` could be lowered without a privacy card; filed captures copied audio into every binder; cloud folder names can reveal binder names; a brain's own rationale was shown as the evidence; registration commands put the token into shell history; the app's automation surfaces were unconsidered. Changed: the widening list, per-binder filed copies as capture-event-v0 §9 says, an honest backup row, Sprava-resolved excerpts first on brain cards, the app running the CLI itself with a recognizable token prefix, and window-only commands with Touch ID for widening changes (4.5, 6.1, 7.5, 9.1, section 8, 2.1).
- The clerk's plan did not match its spec (budget). Changed: a separate binder call, a six-item rerun rule, a first-block document call with code scanning the rest, streaming to keep finished items (with a spike), a bounded meeting reading, round-robin scheduling, a `related` relation for the duplicate call, redacted items included in retrieval, a variant-based release gate with a stated fallback, and a re-measured table (5.1, 5.3, 5.4, 5.5, section 8).
- Hub coexistence (format). The outbox acknowledgement could erase a check-off the hub had just written; lifeproj's proposed refusal would miss adopted but unmigrated binders and break every terminal digest with a non-zero exit; closures could not reach the hub with `closed[]` off; setting a binder to `none` left its old slice in the spool; aliases would flip with lifeproj publishing too; and mechanical repairs wrote into the middle of a terminal digest. ## Appendix A. The heartbeat file

The app trusts `runtime/heartbeat.json` only when it validates against this schema (JSON Schema 2020-12, as the rest of the format; decisions.md F10). The schema and the example below were validated on 2026-10-06 with `check-jsonschema`, again after the second pass added `alerts`, `runtime_key` and `watchdog_exits`; an example with an invalid breaker value, a zero inode and an unknown `runtime_key` fails as expected. Unknown fields are allowed, so a newer runtime can add lines without breaking an older app. Error codes are short lower-case words; a culprit is at most 200 characters and never binder content, a binder's folder name or a file name (3.7).

Notes on the fields:

- `last_wake_at` lets the app grade the beat from the later of the last beat and the last wake, and lets restart counts leave wakes out (3.3).
- `xpc_protocol` and `build` let the app notice a runtime left over from before an update (2.1).
- `lease.inode` identifies the lease file. Only the lease holder writes the heartbeat, so a "held" flag would always be true; the app checks the pid's start time against `started_at` instead (3.3).
- `stage_crashes` counts consecutive crashes per risky stage, for the poison-input rule (3.4).
- `alerts.authorized` is the notification authorization status the runtime last read, so the app can show "Alerts are off" in red (3.7). `runtime_key` is `readable`, or `locked` or `missing` when approvals are paused (4.1).
- `watchdog_exits` counts the watchdog restarts a job caused; it is reloaded from `runtime/breakers.json`, so it survives the restart it caused (3.4).
- Job keys are a job name, or a job name and an opaque binder id for per-binder jobs such as `backup:b2`, never `meta.name`. `last_outcome` separates `skipped` from `ok`, so a run that did nothing never reads as a success. `expected_cadence_s` and `due_since` let the app grade a job that neither fails nor succeeds, and `wedged` marks a task still running past its budget plus a grace period (3.4).
