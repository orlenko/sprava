Status: working plan, written mid-implementation. It replaces nothing in `docs/mvp.md` or `docs/companion.md`;
it says what is unfinished, in what order it gets done, and who does it. Examples are invented.

## 1. Objective

to-do list on a phone through the companion (decisions.md P19). Quality follows the review and test process
v0.3 (`AGENTS.md`): one review round, the full suite once on the final head, small PRs.

## 3. Tracks

Each track is one worker in its own worktree, with one goal. A track is a series of small PRs, each through
the gate, merged by the worker with `scripts/merge-pr.sh`.

### Track A: pairing on the Mac (`mac-pairing`)

Goal: the person can connect the Mac to a relay and pair or remove a phone from the app.

1. Runtime handlers for the reserved requests: `companion_pairing_start`, `companion_pairing_poll`,
   `companion_pairing_confirm`, `companion_devices`, `companion_device_remove`, `companion_reset`, on the code
   the seven PRs land.
2. Settings › Phone: the relay's address and setup code, claim, the pairing QR code and the six-digit check,
   the list of paired devices, Remove.

Done when: on a development build against a local relay (`companion/relay`, file storage), the web app pairs,
shows up in the device list, and stops working after Remove.

### Track B: publishing and requests (`mac-sync`)

Goal: a shown binder's to-dos reach the phone, and what the phone does comes back.

1. Start `CompanionJob` in the runtime, with its budget, breaker and Health line (architecture 3.4): publish
   the index and views, drain requests, publish outcomes. Off until a relay is claimed.
2. "Show on my phone" in each binder's settings, off by default (companion.md §2, principle 6).
3. The cards for phone requests the Mac will not apply by itself (companion.md §6), shown where other cards are.

Done when: with Track A, a to-do added on the Mac appears in the web app within a publish cycle, Done on the
phone closes it on the Mac with Undo, and a stale Done becomes a card.

### Track C: the web app (`web-pwa`)

Goal: the web app is good to use on a phone and can be published the moment the owner names its address.

1. Look at every screen at phone width against the local relay with invented data (Today across binders, a
   binder's Now page, an item, the note editor, pending actions, pairing): fix what makes the to-do list hard
   to use. Installable: manifest, icons, offline shell.
2. A GitHub Actions workflow that builds the web app from a release and publishes it to GitHub Pages
   (companion.md §9). It publishes nothing until the owner sets the address and turns Pages on.
3. An end-to-end script: local relay, built web app, a development Mac build; pair, publish, act, read the
   outcome. It becomes the smoke check for Tracks A and B.

### Track D: the app, for daily use (`app-polish`)

Goal: nothing on the list of known rough edges stops daily use.

In this order, one PR each: #623 (choose a Drafts folder), #626 (the racing test), #593's remaining part,
the Health line issues (#570, #572, #573, #574, #576, #577, #580), #487, then `AGENTS.md` "Build facts" and
`README.md` (Xcode is required). Then check #592, #594 and #582 against main and close what is done, with the
commit that did it.

## 4. Order and shared files

- The seven companion PRs land first, by the lead. Tracks A and B start from that stack's tip and rebase onto
  main once it has merged; the rebase drops the commits main already has.
- Track A owns `Sources/SpravaApp/Settings` for the Phone screen. Track D does not restructure Settings while
  Track A is open. Track B owns the binder's settings page for its one switch.
- Tracks A and B both add lines to the command table and the runtime's wiring. Whoever merges second rebases.
- Track C touches `companion/web` and `.github` only.
- Changes under `Sources/sprava-runtime/**` and the companion files on the sensitive-path list are tier B: the
  local review and the cloud review.

## 5. After these tracks

In this order, each its own plan when its turn comes:

1. Deploy the relay and publish the web app (owner's steps, section 6), pair the real phone.
2. Notifications (Web Push), then the Android share target (companion.md §11, steps 5 and 6).
3. A remote interface for another computer of the person's, over a private network: not designed yet. The
   companion's views and requests are the likely base. Daily use decides how much of the app it must carry.
4. The notarized disk image and the MVP's 30 counted days (mvp.md §7).

## 6. The owner's part

Decisions:

1. The web app's address. It must be an origin that serves nothing else (companion.md §9): a subdomain of the
   owner's, or a GitHub organisation made for it. Recommendation: a subdomain.
2. Where the relay runs: a small hosted container and a bucket, as designed; or on the owner's Mac over a
   private network, which needs a decision recorded. Recommendation: hosted.
3. Close the October PRs and branches of section 2.

Steps only the owner can take: approve Sprava in Login Items; the invented-binder trial, backup and a restore
drill (`docs/daily-workflow.md`); import the first real binder; deploy the relay; turn on GitHub Pages.
